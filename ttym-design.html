ttym

마스터 가이드 · 2026-04-21 · 사용자부터 응용 개발자까지 · master @ 41f7c62
ttym은 한 PTY를 터미널·브라우저·네이티브 앱에서 동시에 보고 조작하는 멀티플렉서다. 서버를 재시작해도 세션이 살아남고, AI 에이전트에게 프롬프트를 던지고 응답 완료까지 기다리는 동작이 API에 내장되어 있다. 사용자가 알아야 할 명사는 둘, 동사 그룹은 다섯이다.
목차 무엇인가 멘탈모델 첫날 5단계 명령 그리드 주소와 컨텍스트 workspace session interaction tty web 에이전트 아키텍처 HTTP API SSE 이벤트 WebSocket 출력·에러

01무엇인가

ttym은 PTY(pseudo-terminal)를 서버에 살려두고, 클라이언트가 자유롭게 붙었다 떼었다 할 수 있게 한다. tmux와 같은 계열이지만 세 가지가 다르다.

축tmuxttym
transport터미널 attach 하나터미널 · 브라우저 · 네이티브 앱 셋, 동시
서버 재시작 내성없음 — 서버 죽으면 모든 세션 소실있음 — 서버 재시작해도 세션 유지
AI 에이전트 연동없음send/await/Stop hook이 1급 동작

tmux 사용자에게 1초 매핑

02멘탈모델 — 한 화면

명사 둘
─────────────────────────────────────────
  workspace  ⊃  session

  workspace  ─ 작업 공간. layout(pane tree) + 그 안의 session들.
  session    ─ PTY 하나. 이름과 role을 가진다.


동사 그룹 다섯
─────────────────────────────────────────
  COMMUNICATE   tty · web · pick           양방향 연결 (사람 ↔ PTY)
  SUBMIT        send · await               단방향 입력 (스크립트 / agent)
  OBSERVE       ls · screen · whoami       읽기만
  LIFECYCLE     new · kill · move · rename 탄생·죽음·이동
  ADMIN         workspace · server · agent 구조 변경 (드물게)


주소 한 줄
─────────────────────────────────────────
  core                workspace 이름
  core:claude         workspace 안 session
  :claude             current workspace 안의 claude
  #42                 raw session id (디버그/도구용)


시각화

  │                              │

  │  └─────────────────────┘     │
  │                              │
  └──────────────────────────────┘

03첫날 — 5단계

$ ttym new claude
  → current workspace 에 "claude" 라는 이름의 session 을 만든다.
    claude 명령을 실행하고 즉시 터미널이 그 PTY 에 꽂힌다.

(claude 화면이 떠 있는 상태에서)
$ C-b d
  → attach 만 떼낸다. claude 는 서버 안에서 계속 살아 있다.

$ ttym await :claude -- '현재 실패하는 테스트 원인만 요약해줘'
  → claude 에게 프롬프트 전송, 응답이 완료될 때까지 대기.
    stdout 으로 클린한 응답 텍스트가 나옴.

$ ttym web :claude
  → 같은 claude session 을 브라우저에서 연다 (URL 출력 + open).
    터미널에서 떼냈어도 브라우저에서 계속 본다.

$ ttym tty :claude
  → 다시 터미널로 돌아가기.

이 다섯 명령이면 일상 사용은 끝이다. 추가로 배울 건 ls, kill, pick, 그리고 옵션 몇 개.

ttym attach는 ttym tty의 영구 alias다. tmux 근육기억을 위해. 포괄 동사(detach · rename)는 session 아래로 내려 의미역 충돌을 피한다.

new의 옵션

ttym new <agent|cmd>  [--in <ws>]              # 어느 workspace에 (생략시 current)
                      [--name <n>]             # session 이름 (생략시 자동)
                      [--role <r>]             # agent | executor 등 (optional)
                      [--right-of <target>]    # placement: 어디에 분할
                      [--below <target>]
                      [--ratio 0.5]
                      [--ready-probe none|process-alive|first-output|first-screen]
                      [--no-attach]            # 만들기만, attach 안 함
                      [--ask '프롬프트']        # spawn + await + print 원샷
                      -- <cmd args...>          # 직접 명령 지정시

예시
  ttym new claude
  ttym new claude --in core --name claude-sub
  ttym new bash --no-attach --name runner
  ttym new claude --ask '현재 빌드 에러 요약'

05주소와 컨텍스트

주소 (FQA)

core              workspace 이름
core:claude       workspace "core" 안 session "claude"
:claude           current workspace 안의 claude   (축약)

  gpai/core:claude     label 바뀌어도 canonical id는 유지

context 추론 — --current 안 쓰게 하는 방법

1. 명시 주소(core:claude, :claude, #42)  → 그대로 사용
2. 지금 ttym tty 내부?                    → TTYM_* 환경변수 사용
3. cwd 위로 .ttymrc 가 있나?              → 팀/repo 기본값
4. ~/.ttym/context.json MRU 히트?         → live면 채택
5. interactive?                           → ttym pick 자동 오픈
                                            아니면 에러 + 후보 3개

06workspace

"한 작업 공간" 단위. layout(pane tree) + 그 안에서 사는 session들. project 라벨 하나로 그룹핑 가능. 

workspace
├── id            canonical identity (UUID, 절대 안 바뀜)
├── name          사람이 부르는 이름 ("core", "demo")
├── project?      optional label ("gpai") — 검색·필터용 alias prefix
├── layout        pane tree, 노드는 sessionId 참조
└── sessions      이 workspace 에 속한 session 들 (역인덱스)

수명주기

create   POST /api/v2/workspaces
delete   DELETE /api/v2/workspaces/{wid}?cascade=detach|terminate
              · cascade=detach   (기본) session 은 default workspace 로 옮겨짐
              · cascade=terminate           session 모두 kill

규칙

R-W1. 모든 session 은 정확히 한 workspace 에 속한다. ttym 사용자에게 "workspace 밖 session" 개념은 없다 — 내부적으로 default workspace 가 자동 생성되어 모든 ad-hoc session 을 보관한다.
R-W2. 같은 workspace 안에서 session 이름은 유니크하다.
R-W3. workspace 의 canonical 주소는 id 다. name·project 는 변경 가능한 라벨이고, 스크립트 안정성은 id 가 책임진다.

07session

PTY 하나. 사람이 들어가서 작업하든 에이전트가 살든 같은 모델이다. 

session
├── id             숫자 PTY 식별자 (#42)
├── workspaceId    어느 workspace 에 속하는가
├── name           workspace 내 유니크 별명 (":claude")
├── role?          "agent" | "executor" | …   (optional filter)
├── spec           {command, cwd, terminalProfile}
├── runtime        시스템 read-only 상태
│   ├── terminal   {cols, rows, lastSeq}
│   ├── process    {pid, state, exitCode}
│   └── agent      {kind, externalSessionId, activeInteractionId}
├── annotations    user patchable key/value
├── snapshot       현재 화면
└── interactions[] await 의 1급 리소스

상태기계

       new
        │
        ▼
   ┌─ spawning ─┐  readyProbe 진행
   │            │
   │            ▼
   │       ready  ◄─── session.ready SSE 이벤트
   │            │
   │            ▼
   │       attached  ◄─── 한 명 이상 client 연결
   │       │       ▲
   │       │       │  attach/detach
   │       ▼       │
   │       detached ┘  (PTY는 살아있음)
   │            │
   │            ▼
   └────► exited  ◄─── child process 종료
              │
              └─► 30초 linger 후 holder 자체 종료

규칙

R-S1. session 의 workspaceId·name 은 PATCH 로 직접 변경할 수 없다. 이동은 POST /sessions/{sid}/move 원자 endpoint 로만.
R-S2. 같은 session 에 여러 client 가 attach 가능. resize 권한은 최근 control client 가 갖는다 (last-controller-wins). view 권한은 resize 안 함.
R-S3. --view 는 transport 플래그가 아닌 session capability 다. view 로 붙은 동안 서버는 HTTP /input·/await 도 거부한다. 우회 불가.

08interaction — await의 1급 리소스

agent에게 프롬프트를 던지고 응답 완료를 기다리는 한 단위. 서버가 상태기계를 소유하므로 브라우저에서도 동일한 동작이 가능하다. 

interaction
├── id            "int_01J…"
├── sessionId     누구에게 보낸 prompt 인가
├── input         {text, encoding}
├── submit        {mode, profile}   ← agent kind에 따라 자동 (CR/LF)
├── completion    {strategy, timeoutMs}
└── result        pending | completed | timed_out | failed
                  + snapshot, lastSeq, capturedAt

예시

POST /api/v2/sessions/42/await
{
  "input":      { "text": "현재 실패 테스트 원인 요약" },
  "submit":     { "mode": "agent-default" },
  "completion": { "strategy": "agent-stop", "timeoutMs": 60000 },
  "response":   { "snapshotFormat": "plain" }
}

200 OK     완료
202 Accepted   timeout — Location 헤더로 interaction id 반환
               GET /api/v2/sessions/42/interactions/{iid} 로 이어받기
timeout 은 에러가 아니다. interaction 이 아직 진행 중이라는 의미. GET 으로 이어받으면 결국 completed 가 된다.

09tty — 터미널 transport

ttym tty <target> [--view] [--prefix C-b]

native 터미널에 raw 바이트를 그대로 전달한다. xterm 호환이면 무엇이든 동작.

attach 내부 키 (prefix 기본 C-b)

C-b d       detach (떼기)
C-b s       picker (workspace 안 다른 session 으로 전환)
C-b n       next session
C-b p       prev session
C-b ?       도움말
C-b C-b     prefix 자체를 inner shell 로 전달
C-]         alternate detach

view 모드

ttym tty :claude --view
  · 화면은 보이지만 입력 안 됨
  · 회의에서 동료에게 보여줄 때, agent 작업을 관전할 때
  · 서버가 input 거부를 enforce — WS 우회 불가

10web — 브라우저 transport

ttym web <target> [--view] [--print]

브라우저로 같은 session 을 연다. --print 는 URL 만 출력하고 자동 open 안 함. 

URL 라우트
  http://<host>:7690/s/{sessionId}     session page
  http://<host>:7690/w/{workspaceId}    workspace page (layout 전체)

브라우저 클라이언트
  · @ttym/client (xterm.js + WebGL 렌더)
  · 같은 ttym.mux.v2 WebSocket 프로토콜 사용
  · tty 와 동일한 capability/view 모델
같은 session 을 터미널과 브라우저에서 동시에 열어도 된다. 두 화면 모두 같은 PTY 출력을 받고, input 은 서로의 화면에 반영된다 (이론적으로 협업 가능).

11에이전트 연동

Claude Code 와 Codex CLI 같은 인터랙티브 AI 에이전트를 session 안에 띄워두고 send/await 로 프로그래밍한다.

submit 규약 — 사용자는 의식하지 않는다

runtime.agent.kind 에 따라 send/await 가 자동 처리:

  claude-code    텍스트 전송 후 CR (0x0d) 자동 append
  codex          텍스트 전송 후 CR 자동 append
  shell (zsh 등) 자동 append 없음  ← 사용자가 $'\n' 직접
  unknown        자동 append 없음

raw byte 가 필요할 때:
  ttym session input <target> -- <bytes>   (내부/디버그용)

hook 설치 — await 의 토대

ttym agent install claude
  · ~/.claude/settings.json 에 SessionStart + Stop 훅 추가
  · Stop 훅이 interaction 완료를 ttym 서버에 신고 (HTTP)
  · await 가 이 신호로 응답 완료를 감지

ttym agent install codex
  · ~/.codex/config.toml [features] codex_hooks=true
  · ~/.codex/hooks.json 에 Stop 훅 등록

한 줄 워크플로

# 띄우면서 바로 질문 (spawn + await)
ttym new claude --ask '현재 빌드 에러 요약해줘'

# 이미 있는 claude 에 질문
ttym await :claude -- '다음 단계 제안'

# 여러 에이전트 병렬 (각자 다른 await 가 독립적으로 완료 감지)
ttym await :claude-a -- '코드 리뷰' &
ttym await :claude-b -- '테스트 보강 제안' &
wait

왜 holder 가 분리됐나

holder 는 PTY 하나당 독립 Rust 프로세스 다. server 는 holder 들에 Unix socket 으로 붙는 client 일 뿐 — PTY 의 소유자가 아니다. 이 구조 덕분에:

  • 서버 hot-reload 가 안전. ttym server restart 해도 holder 와 PTY 는 살아 있다.
  • 장애 격리. holder 하나가 패닉하면 그 session 만 영향. 다른 session 멀쩡.
  • recovery 자동. server 부팅 시 ~/.ttym/session-*.json manifest 를 스캔해서 살아있는 holder 들에 재접속.

계보: dtach (2004, Ned T. Crigler — "screen 의 detach 만") 의 wire 단순함 + conmon (CRI-O 의 container monitor) 의 orchestrator-survivable 철학을 PTY 세계로 가져온 것.

3-Plane

┌── CONTROL  (HTTP / JSON) ───────────────────────────────────────┐
│  CRUD · 의미적 요청 (await) · stateless                          │
└─────────────────────────────────────────────────────────────────┘
┌── WATCH    (SSE, text/event-stream) ────────────────────────────┐
│  상태 변화 구독                                                  │
└─────────────────────────────────────────────────────────────────┘
┌── DATA     (WebSocket, subprotocol ttym.mux.v2) ────────────────┐
│  저지연 terminal IO                                              │
└─────────────────────────────────────────────────────────────────┘

책임이 분리되어 있어 디버깅·확장이 단순하다.

15WebSocket wire spec

Handshake
  Sec-WebSocket-Protocol: ttym.mux.v2
  (subprotocol 없음 → legacy v1 fallback, 기존 클라 보호)


Single WebSocket. 프레임 타입은 WS opcode 로 구분:
  TEXT   frame  → control plane JSON
  BINARY frame  → data plane bytes (terminal IO)


control (TEXT JSON, 한 줄)
  {"type":"attach","sessionId":42,"fromSeq":120,"mode":"control",
   "terminal":{"cols":120,"rows":40}}
  {"type":"attached","sessionId":42,"lastSeq":125,"capability":"control"}
  {"type":"detach","sessionId":42}
  {"type":"resize","sessionId":42,"cols":120,"rows":40}
  {"type":"pause-view" | "resume-view","sessionId":42}
  {"type":"error","sessionId":42,"code":"…","message":"…"}


data (BINARY, little-endian)
  [opcode:u8] [sessionId:u32] [seq:u32] [payload:bytes]

    opcode 0x01 = data_out     (server → client, seq 유효)
    opcode 0x02 = data_in      (client → server, seq=0)
    opcode 0x03 = ack          (seq 필드가 수신확인, payload 없음)


invariants
  · sessionId 는 u32LE
  · seq 는 server-side monotone, 0 은 "seq 없음"
  · view capability 에서 data_in 은 서버가 drop + error 통보
  · CREATE/LIST 같은 lifecycle 은 WS 에 없다 — HTTP 전용

  ttym.log

이 문서는 ttym 의 사용자 표면(명사·동사·주소)부터 응용 개발자 표면(HTTP/SSE/WS)까지 한 페이지에서 다룬다. 구현 세부(holder Rust 코드, server-manager 내부, agent-bus 스키마)는 holder/src/main.rs·server/src/·client/src/ 의 코드와 주석을 참조.
