ADR-0001 — 세션은 어디에 속하는가

표면(주소 체계·동사·저장 포맷)을 바꾸기 전에 닫아야 하는 네 가지 결정. 카운슬의 규칙은 하나라도 미확정이면 저장 포맷을 바꾸지 않는다였다. 아래 네 답은 전부 코드와 프로덕션 데이터에서 나온 추천이며, 승인되면 D2(문법)·D3(shadow projection)의 전제가 된다.

상태
제안됨 — 승인 대기
날짜
2026-08-06
근거
A1·A4 구현 경험 · C3 프로덕션 fixture · 아키텍처 카운슬 · 8개 프로젝트 비교
바꾸는 것
결정만. 저장 포맷·코드 무변경 (핵심 귀결: v2→v3 포맷 변환 자체가 취소된다)

Q1. 세션 : workspace — 정확히 하나인가, 많아야 하나인가

선택지내용대가
(a) 정확히 1RFD 1의 답. 미지정 생성은 default workspace가 흡수모든 생성 경로가 workspace 장부를 통과해야 함. API로 만든 세션·테스트·도구가 전부 "소속 부여" 절차를 짊어짐
(b) 0 또는 1세션은 독립 존재. workspace가 세션을 참조한다. 한 세션은 많아야 한 workspace에미소속 세션은 이름이 없어 #id로만 주소됨
(c) N (여러 곳에 표시)같은 세션을 여러 workspace에제거·이름 유일성 의미론이 전부 복잡해짐. 관측된 수요 0

추천: (b). 근거는 셋이다.

  • 현실이 이미 (b)다. POST /api/sessions는 소속 없이 세션을 만들고, 오늘 아침 프로덕션에 미소속 세션 5개가 실재했다(950·982·995–997). (a)는 이 현실 위에 "default workspace"라는 장부를 덧씌우는 것일 뿐, 정보를 더하지 않는다
  • headless 조작과 맞다. 스크립트가 세션 하나를 띄워 쓰고 버리는 경로에 workspace 의례가 없어야 한다 — claude-squad가 tmux를 쓰는 방식이 정확히 이것이다
  • (c)를 지지하는 관측이 없고, 카운슬의 규칙은 "관측되지 않은 요구를 설계하지 않는다"였다

CLI의 ttym new claude가 이름을 가지려면 어딘가 소속돼야 하는데, 그건 CLI가 default workspace에 넣어주는 편의로 층을 위에 올린다. 저장 모델의 불변식이 아니다.

Q2. 소속 세션은 반드시 layout leaf여야 하는가

선택지내용대가
(a) 예 — layout이 유일한 장부RFD 1의 A-2. members[] 삭제, 소속 = leaf 존재배치 없는 세션·최소화·나중 배치가 전부 불가능. headless를 지향하며 headless 세션을 금지하는 자기모순 (카운슬 04)
(b) 아니오 — members가 장부, layout은 표현불변식은 한 방향만: 모든 leaf는 member다 (유령 pane 금지). 역은 강제 안 함 — 미배치 member는 합법(= headless/최소화)두 장부의 정합을 관리해야 함

추천: (b). 그리고 이것은 새 설계가 아니라 A1·A4가 이미 구현한 것의 승인이다.

  • A1: 모든 mutation이 members[]와 layout을 한 연산에서 함께 갱신한다
  • A4: 미배치 member를 삭제하지 않고 보존 + 진단한다 (workspace-store.ts:352). leaf인데 member가 없으면 member를 자동 생성한다 — (b)의 불변식 그대로
  • "두 장부 정합" 비용은 A4의 검증기가 이미 지불했다 — 정상 경로에서 진단 0건이 테스트로 고정돼 있다

귀결 — RFD 1 §5.1의 A-2(소속 모델 변경)는 폐기한다. 따라서 workspaces.json의 일방향 v2→v3 변환도 필요 없어진다. RFD 6.2가 경고했던 "되돌릴 수 없는 변환"이라는 위험 항목이 로드맵에서 사라진다. C3의 fixture 테스트가 v2 왕복을 이미 고정하고 있다.

Q3. layout — 서버 전역 문서인가, 클라이언트별 view인가

선택지내용대가
(a) 서버 전역 하나workspace당 layout 하나. 동시 편집은 layoutVersion(409)으로 검출web과 desktop이 같은 배치를 공유
(b) 클라이언트별클라이언트 identity마다 layout 저장저장·동기화·"split은 누구의 layout을 바꾸나" 의미론 전부 신설. 사용자 1명에서 관측된 수요 0

추천: (a). 실제로 아팠던 것은 layout 파괴(A1이 해결)였지 클라이언트 간 경합이 아니다. 줌·일시 최대화 같은 표시 상태는 클라이언트가 로컬로 갖되 저장하지 않는 것으로 충분하다. (b)는 카운슬의 판별식(독립 배포 소비자가 실재할 때)을 통과하는 날 다시 연다.

Q4. name · role · tags — session 속성인가 membership 속성인가

선택지내용대가
(a) session 속성RFD 1 §5.1의 답 (N2: workspace 안 유일)미소속 세션의 이름 유일성 범위가 정의 불능. "workspace 안 유일"이라는 규칙 자체가 소속을 전제 — 속성의 자리와 규칙의 자리가 어긋남
(b) membership 속성이름은 소속의 산물. 미소속 세션은 #id로 주소같은 세션이 workspace를 옮기면 이름을 다시 받는다

추천: (b). 유일성의 범위(workspace)가 곧 속성이 사는 곳이어야 규칙이 자연스럽다. role·tags도 "그 workspace에서의 역할"이므로 같은 자리다. 그리고 지금 저장이 이미 (b)다 — WorkspaceMemberInfo가 name·role·tags를 든다. 마이그레이션 비용 0.

종합 — 승인되면 확정되는 모델

session      독립 존재. id·cmd·geometry·runtime을 가짐. 이름은 없음
workspace    session에 대한 참조(membership)의 컨테이너
membership   name(workspace 안 유일)·role·tags. 배치와 독립
layout       membership의 부분집합을 배치하는 표현. workspace당 하나
불변식        leaf ⊆ members  (유령 pane 금지 — 위반 시 member 자동 생성)
             members ⊄ leaf 허용 (미배치 = headless/최소화, 진단만)

D2가 이 위에서 할 수 있게 되는 것

주소 ws:name은 membership을 해석하고, #id는 세션을 직접 가리킨다 — 미소속 세션도 항상 주소 가능. new(미소속 또는 default 편의)와 split(배치 동반)의 의미가 갈라지는 근거가 이 모델이다.

명시적으로 닫는 문 — 나중에 "왜 없지"로 다시 싸우지 않기 위해.

세션의 다중 workspace 표시(Q1-c) · layout의 클라이언트별 저장(Q3-b) · layout을 유일 장부로 승격(Q2-a, RFD 1 A-2). 셋 다 재개 조건은 같다: 독립 배포된 두 번째 소비자의 실재하는 요구.

이 문서가 승인되면 상태를 승인됨으로 바꾸고 D2(CLI 문법 — alias 우선)로 진행한다. 저장 포맷은 계속 v2다. 코드 변경은 이 문서에 없다 — A1·A4가 이미 이 모델을 구현했다는 사실의 확인이 이 문서의 절반이다.
