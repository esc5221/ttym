Internals

How ttym works inside

ttym keeps each terminal in its own small process, outside the server. Sessions that survive a server restart, upgrades that close nothing, and agents that sleep and wake all depend on that split. Each section below summarizes a document in the repo and links to it; the documents are the reference.

01

One server, one holder per terminal

The server is the only hub. Every viewer talks HTTP and WebSocket to it, and only the server talks to holders, over a unix socket. A holder is a Rust process of about 1 MB that owns one PTY and a ring buffer of its output. The CLI has two roles: ttym attach is a viewer like the browser, and the other verbs (new, split, send, await) are a control plane over plain HTTP.

  • Emulation lives in the server. The holder only knows bytes; the server runs a headless xterm per session. Keeping the cell model out of the holder means a replacement server does not have to agree with the holder on screen state, and the holder stays small enough to run for weeks.
  • One protocol for every viewer. The CLI's attach, the browser and the desktop app all speak the same HTTP + WS protocol, implemented once in @ttym/protocol for both ends.
  • Version checks stop early. API_VERSION covers the whole HTTP + WS surface. The CLI reads /api/version and stops with exit code 5 when its version is outside the range the server supports, instead of running half-compatible.

02

Surviving the server

When the server stops, holders keep their PTYs and keep recording output. A new server reconnects to each holder's socket, claims it, and catches the screen up from a checkpoint plus the bytes written since.

Frames

Holder and server exchange [u32 len LE][u8 cmd][payload]. Output frames advance a running byte offset in the holder, which is what DUMP_SINCE and checkpoints refer to.

Checkpoints

The server writes a rendered-ANSI checkpoint per session after 2 s of quiet, and at most 30 s apart. A full 3,000-row screen fits in about 571 KB, while the raw ring holds roughly a third of that history, so seeding from the checkpoint restores more screen than replaying the ring.

Gaps are reported

If the requested offset has already left the ring, the holder answers gap=true. The server reports the gap instead of presenting a partial screen as a complete one.

One controller

A holder accepts one controlling server. Before the lease frames existed, a new connection silently evicted the old one, and two racing servers could lose sessions. Now a second server gets DENIED unless it asks for takeover.

Sockets heal

A holder checks its socket path every 5 s and rebinds if the file is gone. Without it, a deleted socket would leave a live PTY that nothing can reach.

Upgrades by rename

ttym upgrade puts the new build next to the old one and swaps them by rename. Running processes keep their open files (POSIX), only new processes load the new binaries, and a failed health check swaps back.

03

The wire: seq numbers, snapshots, deltas

Viewers get output as numbered frames. A viewer that reconnects says which seq it has, and the server sends either the missing deltas or one snapshot of the whole screen followed by deltas.

u16 sessionId LEu8 cmdu32 seq server → client DATA, SNAPSHOTpayload

DATA has two shapes

Server-to-client DATA carries a seq; client-to-server DATA is raw key bytes. Each direction has its own decoder (decodeServerFrame, decodeClientFrame). A single symmetric decoder once read the first 4 bytes of any input frame of 7 bytes or more as a seq, and characters vanished whenever a Korean IME committed a syllable and a space in one frame. A regression test drives a real PTY through that case.

Snapshots in one write

The client applies a snapshot as \x1bc plus the screen in a single xterm write. One write chunk is parsed atomically, so the reset and the repaint land in the same frame; calling term.reset() first would paint an empty frame and flicker.

Snapshots carry a seq

The seq on a snapshot is the watermark it was rendered at. The client moves its fromSeq to it, so a resync does not fall back into another snapshot.

04

Agents as functions

ttym await sends a prompt to an agent's terminal and blocks until that turn ends, then returns that turn's answer. The end of a turn comes from the agent's own Stop hook, not from watching the screen, so a long pause in the output does not end the wait early.

# SessionStart / Stop / StopFailure / SessionEnd hooks
ttym agent install claude
ttym workspace add --current --name helper --role agent --cmd claude
ttym await :helper --json -- "Why does this stack trace happen?"

Markers, not row numbers

After the scrollback moves, a row number still falls inside the buffer but points at someone else's output. An xterm marker moves with its line; if it scrolls out of the buffer (line = -1) the result is null instead of the wrong rows.

Parallel by default

Each await is its own interaction keyed to its session, so several agents can be awaited at once and each completes on its own Stop hook.

Codex too

Codex CLI supports a Stop hook behind the codex_hooks feature flag (0.114+). With it installed, await works the same way.

05

Sleep and wake

An idle Claude Code process holds 200 to 600 MB. After 30 minutes without input or output (configurable, or off), ttym stops the agent and keeps its screen. The next keystroke, send or await resumes the same conversation, and the input waits in a queue until the agent is ready.

What counts as busy

Checked in this order, most authoritative first. Any one of them keeps the agent awake.

  1. ~/.claude/sessions/<pid>.json status: waiting (a permission prompt or dialog, which a resumed agent could not answer) or busy
  2. A turn opened by a prompt and not yet stopped
  3. In-flight work from the last Stop hook payload: background tasks, and scheduled wakeups that sleeping would lose
  4. Fallback for older versions: a command still running under the agent

Measured

wake, Claude Code    1.7 s
wake, in the film    2.5 s
RAM returned (film)  374 MB
wake, Codex          ~4 s
sleeps per tick      3, 3 s apart

Codex takes longer because it has no prompt hook and sends SessionStart only on its first turn, so readiness is detected from the process instead. While asleep, ATTACH, SNAPSHOT and ttym screen return the frozen screen, and it survives a server restart.

06

Remote access, checked

The server listens on 127.0.0.1. Remote access goes through a tunnel or tailscale serve, and every request passes the same gate. The gate first decides whether a request came from this machine, because the CLI, agent hooks and the local web UI need no login.

  1. Where did it come from?

    localpeer is loopback, Host is loopback, no proxy headersno login
    local-proxya proxy on this machine for a browser on this machine: Host allow-listed, no Cloudflare or Tailscale headers, every forwarded client loopbackno login
    remoteanything else: a non-loopback peer, a loopback Host with proxy headers, any other Hostcontinue ↓

  2. Is the Host on the allow-list?

    No → 403. This also blocks DNS rebinding, where a hostile site's name resolves to 127.0.0.1.

  3. Is there a valid login cookie?

    ttym_session: HttpOnly, SameSite=Lax, 30 days, Secure when the request arrived over HTTPS. Yes → pass.

  4. Does a trusted identity check out?

    TailscaleThe Tailscale-User-Login header is only a claim. The login must be trusted, the last forwarded hop must be a tailnet address (100.64.0.0/10 or fd7a:115c:a1e0::/48), and tailscale whois for that address must name the same login.
    Cloudflare AccessThe Cf-Access-Jwt-Assertion JWT is verified RS256 against the team's published keys, with issuer, app aud and expiry pinned, and the email checked against ttym's own list. A loosened Access policy still lets no other email in.

    Yes → the usual 30-day cookie is issued. One login (the Tailscale account or the Access PIN) opens ttym.

  5. Otherwise: a one-time link

    ttym remote link mints a link valid for 10 minutes and one use. The token sits in the URL fragment, which browsers do not send in requests. This is the way in for paths that carry no identity: the LAN, a local nginx, a device on another tailnet account.

  • Writes and WebSocket upgrades must come from the same origin, and the server sends no CORS headers.
  • The allow-list, trusted identities and signed-in browsers live in ~/.ttym/remote.json (mode 0600, tokens stored as hashes). Only local callers can change them.
  • ttym remote tailscale and ttym remote cloudflare are non-interactive, take --json and are safe to re-run, so an agent can do the setup.

Source: docs/remote-access.md · packages/server/src/remote

07

Shell integration

With one line in ~/.zshrc, the shell marks where each prompt, command and output starts (OSC 133/633) in its own output. The server indexes those marks, so plain shells become scriptable without scraping prompts.

# ~/.zshrc; does nothing outside ttym panes
[[ -n "$TTYM_SESSION_ID" ]] && source ~/.local/share/ttym/scripts/ttym-shell-integration.zsh

# ✓/✗, exit code, duration, command line
ttym commands :build
# one command's output, cut at the marks
ttym output :build --cmd 3
# send, wait for the end mark, get exit code + output
ttym await :build -- "make test"

await picks its path from evidence: a pane that has shown integration marks gets the command path, and agent panes keep the Stop hook path. In the web terminal the same marks drive ⌘↑ / ⌘↓, which jump between command boundaries in the scrollback.

Tests

422 tests. They spawn real holders, drive a real PTY through the WS protocol, and replay a de-identified capture of a production runtime directory (7 workspaces, 180 snapshots, 241 meta files) to pin boot, recovery and on-disk format round-trips. The CLI end-to-end tests run the built dist/ttym.

The runtime directory is cleaned at boot and daily: sessions that are neither live nor workspace members lose their snapshot and meta after 14 days (TTYM_GC_DAYS).
