1. 범위와 방법

비교 대상은 두 계보로 나뉜다. 하나는 PTY를 프로세스 경계 밖으로 밀어내는 문제를 20년 넘게 다뤄온 계보(dtach → abduco, tmux, mosh, conmon)이고, 다른 하나는 2026년에 coding agent 여러 개를 동시에 다루려고 등장한 계보(claude-squad, vibetunnel, cmux, paseo, orca)다. ttym은 전자의 구조 위에 후자의 목적을 얹고 있어서, 두 계보를 같은 표에 놓아야 위치가 보인다.

확인은 clone한 소스를 직접 읽어서 했다. 파일:줄 번호가 붙은 주장은 코드에서 확인한 것이고, 문서만 근거인 항목은 문서로 표시했다. 확인하지 못한 칸은 비워두지 않고 미확인이라고 적었다 — 빈칸은 "해당 없음"으로 오독되기 때문이다.

비교의 한계. 저장소 크기가 242MB(orca), 383MB(cmux)에 달해 전수 조사는 하지 않았다. 각 프로젝트에서 PTY 생성 지점 · 세션 지속성 · 스크롤백 저장 · agent 훅 네 갈래만 추적했다. 따라서 이 문서는 "이 축에서 이렇게 다르다"는 주장은 하지만 "A가 B보다 낫다"는 총평은 하지 않는다.

2. 각 프로젝트의 방향성

2.1 지속성 계보 — PTY를 어디에 둘 것인가

abduco (2014, C, 268KB). dtach의 후계. 하는 일은 하나다 — 프로그램을 PTY에 넣고 그 PTY를 자기 프로세스가 소유한 뒤, 클라이언트가 붙었다 떨어지게 한다. 터미널 에뮬레이션을 하지 않고 스크롤백도 갖지 않는다. 붙어 있는 동안의 바이트를 그대로 흘려보낼 뿐이다. 의도적으로 최소다.

tmux. 서버 프로세스가 pane마다 grid(셀 배열)를 소유한다. 클라이언트는 그 grid의 뷰일 뿐이다. 그래서 클라이언트가 죽어도 세션이 살고, 여러 클라이언트가 같은 세션을 볼 수 있다. 대신 서버가 죽으면 전부 죽는다 — tmux의 설계는 서버가 죽지 않는다는 전제 위에 있다.

mosh (MIT, 2012). 문제를 재정의했다. 터미널을 "바이트 스트림을 전달하는 파이프"가 아니라 "동기화해야 할 상태 객체"로 본다. 서버가 터미널 에뮬레이터를 돌려 Framebuffer를 만들고, 클라이언트와 그 객체의 diff만 교환한다. 네트워크가 끊겨도 재연결 시 "최신 화면으로 fast-forward"하면 그만이다.

mosh/src/terminal/terminalframebuffer.h:396class Framebuffer
{
  // To minimize copying of rows and cells, we use shared_ptr to
  // share unchanged rows between multiple Framebuffers.
  ...
  rows_type rows;          // 뷰포트 행들. scrollback 없음

결정적 한계도 여기 있다. rows는 뷰포트만이다. mosh에 스크롤백이 없다는 오래된 불만은 버그가 아니라 이 설계의 직접적 귀결이다.

conmon (CRI-O). 컨테이너 런타임이 죽어도 컨테이너 프로세스가 살아남도록 PTY와 감시를 별도 프로세스로 분리한다. ttym의 holder와 같은 형태다. 출력은 메모리가 아니라 파일에 쓰고 --log-size-max로 제한한다.

2.2 agent 계보 — 여러 agent를 어떻게 다룰 것인가

claude-squad (Go, 47파일). 가장 얇다. PTY도 지속성도 직접 하지 않고 tmux에 위임한다. tmux new-session -d -s claudesquad_<name> -c <workdir> claude를 실행하고 git worktree를 붙인다. tmux가 이미 푼 문제를 다시 풀지 않겠다는 판단이다.

vibetunnel (TS 450 + Swift 325). "브라우저를 터미널로 만든다"가 목적이다. 세션마다 디렉토리를 만들고 asciinema cast 파일에 출력을 append한다.

vibetunnel/web/src/server/pty/session-manager.ts:14~/.vibetunnel/control/
├── .version
└── [session-id]/
    ├── session.json    # 메타데이터
    ├── stdout          # 출력 스트림 (asciinema cast)
    └── stdin           # 입력 (FIFO 또는 파일)

파일 기반이라 offset으로 어디서든 이어읽을 수 있고, HQ/remote 구조로 여러 머신의 세션을 한 대시보드에 모은다.

cmux (Swift 8113파일). macOS 네이티브 앱. libghostty로 GPU 렌더링하고 사용자의 기존 ~/.config/ghostty/config를 읽는다. 저자가 동기를 직접 적었다.

cmux/README.md:125I tried a few coding orchestrators but most of them were Electron/Tauri apps
and the performance bugged me. I also just prefer the terminal since GUI
orchestrators lock you into their workflow.

paseo (TS 2707파일 + iOS/Android). 상주 데몬(기본 포트 6767)이 있고 데스크톱·웹·모바일·CLI가 거기 붙는다. PTY는 데몬이 아니라 별도 worker 프로세스가 소유한다 — ttym의 holder와 같은 판단이며, 이유까지 코드에 적혀 있다.

orca (TS 10204 + tsx 1593, Electron). ADE를 표방한다. agent마다 git worktree를 주고, 터미널·에디터·GitHub/Linear·브라우저 프리뷰를 한 앱에 통합한다. PTY는 Electron main 프로세스가 node-pty로 만든다. 플러그인 시스템(plugin-capabilities.ts, plugin-consent-gate.ts)과 consent 모델이 있다.

3.2 재시작 후 무엇이 복원되는가 — 층이 다른 두 해법

이 축이 가장 오해되기 쉽다. "세션 복원"이라는 같은 말이 두 가지를 가리킨다.

구분복원 대상대표얻는 것 / 잃는 것

cmux는 이 구분을 문서에 명시적으로 적었다. 인용할 가치가 있다.

cmux/README.md:249Quitting cmux saves the current session. On relaunch, cmux restores app-owned state:

진단. agent 시대에는 "세션 재개"가 상당 부분 충분하다. Claude Code·Codex가 스스로 --resume <id>를 지원하므로, 대화 맥락은 agent가 책임지고 도구는 id만 기억하면 된다. cmux가 13종 agent의 resume을 지원하면서도 PTY 지속성을 포기한 것은 합리적 트레이드오프이지 태만이 아니다.

반대로 프로세스 지속이 값을 하는 경우는 agent가 아닌 것이 섞일 때다 — 30분짜리 빌드, 붙잡고 있는 REPL, ssh 세션, 로그 tail. ttym 프로덕션의 16개 세션 중 3개가 ssh mini·python tab_monitor.py·caffeinate인 것이 이 차이를 그대로 보여준다.

ttym의 실제 결함. vibetunnel은 이전 내용을 버려도 화면 재구성이 정확한 지점에서만 자른다. orca는 그 정도는 아니지만 최소한 UTF-8 문자를 반토막 내지 않는다. ttym의 ring은 둘 다 하지 않는다 — ring이 넘치면 멀티바이트 문자 중간, ANSI 이스케이프 시퀀스 중간 어디서든 잘린다.

그 잘린 앞머리는 서버 교체 시 DUMP_RESP로 그대로 xterm에 재생된다(session.ts:305-311). 깨진 시퀀스가 파서에 들어가면 이후 렌더가 오염될 수 있다. ring이 넘치지 않는 동안은 드러나지 않는 결함이며, 행당 913바이트를 3000행에 곱하면 2.7MB로 ring 1MB를 넘긴다.

3.4 상태 표현 — raw 바이트인가 셀 그리드인가

ttym RFD 1의 §7.2는 transcript를 원시 바이트 구간으로 자르면 안 되는 이유를 이렇게 적었다. "에이전트 TUI는 같은 행을 반복해서 다시 그리므로 바이트 구간에는 중간 프레임이 모두 포함된다." 이번에 실측한 숫자가 그 주장을 정량화한다.

측정 (holder에 직접 붙어 raw 바이트 캡처 → 동일 설정 headless xterm에 재생)

                        raw bytes    렌더된 행    행당 bytes
Claude Code 긴 응답 1회    94,065        103          913
Codex 짧은 응답 1회        43,319         39        1,111
Claude 부팅 화면만          2,774          7          396

같은 3000행이 raw로는 2.7MB, 렌더된 상태로는 571KB다(프로덕션 snapshot 실측). 4.7배가 전부 redraw 파편이다. 이 사실은 두 군데에 동시에 영향을 준다 — transcript를 무엇으로 자를 것인가(RFD B), 그리고 교체 시 무엇을 보존할 것인가(ring).

paseo는 이 문제를 프로토콜 층에서 이미 해결해 두었다.

진단. captureTerminalLines(start, end)는 RFD 1 §5.3이 제안한 mark 기반 구간 추출과 같은 것이다. revision + replayPreamble은 "snapshot을 깔고 그 이후 delta만 재생"이라는, ttym이 지금 검토 중인 방식과 같다. ttym이 설계하려는 것은 독자 발명이 아니라 이미 출하된 패턴이다 — 이는 설계의 타당성을 높이는 근거이면서, 동시에 차별점이 여기에 있지 않다는 뜻이기도 하다.

includeWrapFlags는 ttym이 고려하지 않은 축이다. 복원된 내용을 resize할 때 soft-wrap을 다시 흘리려면 행마다 wrap 플래그가 필요하다. 없으면 창 크기를 바꾼 순간 복원된 스크롤백이 깨진다.

4. 문제별 심층 진단

4.1 "PTY를 분리한다"의 진짜 비용

ttym·paseo·conmon·abduco가 모두 PTY를 별도 프로세스로 분리했다. 이 결정은 서버 재시작을 견디게 해주지만, 분리 자체가 새 문제를 만든다. 이번 조사에서 ttym이 겪은 세 가지가 전부 분리의 대가다.

  1. 소켓 경로가 유일한 도달 수단이 된다. 같은 id로 새 holder가 뜨면 main.rs:221의 remove_file이 기존 소켓을 지운다. listener fd는 살아 있는데 경로가 없어 아무도 붙을 수 없다. 프로덕션에서 실제로 3건 발생해 있었다.
  2. 복구가 네트워크 연산이 된다. handshake에 timeout이 필요하고(10초), 순차로 돌리면 그 timeout이 세션 수만큼 누적된다.
  3. 버퍼가 프로세스 경계를 넘어야 한다. 그래서 ring이 생기고, ring 크기가 곧 복원 가능한 범위의 상한이 된다.
대조. orca·cmux는 PTY를 앱에 두었으므로 이 세 문제가 아예 없다. 대신 앱을 끄면 빌드가 죽는다. 어느 쪽이 옳은지는 무엇을 세션에 담느냐에 달렸다 — agent만 담으면 분리의 대가가 순손실이고, agent 아닌 것이 섞이면 분리가 값을 한다.

4.2 버퍼를 두 벌 갖는다는 것

ttym에는 지금 같은 내용의 버퍼가 두 개 있다.

holder ring       raw 바이트, 메모리 1MB, 913 B/행     서버 교체 시 사용
서버 snapshot      렌더된 ANSI, 디스크 571KB, 194 B/행   재부팅 시에만 사용

둘은 각각 다른 사고를 대비해 만들어졌다. ring은 "서버가 죽어도 최근 출력을 잃지 않기 위해", snapshot은 "머신이 재부팅돼도 화면을 복원하기 위해". 그런데 boot()의 순서(session-manager.ts:72-76)가 recover()를 먼저 돌리고, holder로 복구된 세션은 snapshot 경로에서 건너뛴다. 교체 시 snapshot은 디스크에 있는 채로 쓰이지 않는다.

같은 3000행을 ring은 2.7MB로 담아야 하고 snapshot은 571KB로 담는다. 4.7배 효율의 자산을 놀리면서 그보다 나쁜 쪽의 크기를 걱정하고 있는 구조다.

다만 3.3의 실측이 이 걱정의 크기를 깎는다. ring이 넘쳐 바이트를 39.6% 잃어도 렌더된 행은 12.8%만 줄었고, 사라진 것은 부팅 배너였다. ring 확대는 교체를 막는 문제가 아니라 구조의 비효율로 다뤄야 한다.

세 갈래 해법과 각각의 실물 선례.
(a) ring을 키운다 — conmon의 --log-size-max 계열. --ring-size 인자는 holder에 이미 있고(main.rs:158) 서버가 넘기지 않을 뿐이다. 가장 싸지만 크기 근거가 없다.
(b) snapshot을 seed로 쓰고 ring은 delta만 — paseo의 revision+replayPreamble과 동형. 재료가 이미 다 있다. DUMP_REQ에 since_seq를 더하고 snapshot에 seq를 기록하면 된다.
(c) 디스크 append + 의미 경계 prune — vibetunnel의 cast 파일. 스크롤백이 사실상 무제한이 되고 asciinema 재생·공유가 덤으로 따라온다. 대신 I/O와 파일 수명 관리가 생긴다.

4.3 "응답만 돌려준다"는 것의 난이도

RFD 1의 B는 mark 기반 구간 추출로 이 문제를 푼다. 이번 측정으로 두 가지가 확정됐다.

첫째, alternate screen은 걸림돌이 아니다. Claude Code를 기준선으로 캡처했더니 RFD가 기록한 관측(?1049h 미출현, ?2004h·?25l 출현)과 정확히 일치했고, 같은 도구로 Codex를 부팅 시점과 실제 응답 중에 두 번 관측했으나 ?1049h·?1047h·?47h 모두 나타나지 않았다. RFD §9의 미해결 항목 하나가 닫힌다.

둘째, 스크롤백 고갈도 걸림돌이 아니다. 긴 응답 1회가 103행으로 3000행의 3.4%다. RFD 6.1이 우려한 "응답 하나가 스크롤백을 밀어낸다"는 29회 대화를 해야 도달한다.

남는 진짜 난제는 "응답"의 경계를 무엇으로 정의하느냐이며, 이건 측정으로 풀리지 않는다. paseo가 UserPromptSubmit을 구독하는 것은 이 경계의 시작점을 추정 대신 사실로 만드는 선택이다. 끝점은 Stop/StopFailure/SessionEnd로 나뉘어 있다. ttym이 Stop 하나만 보는 한, 시작도 끝도 추정이다.

4.4 layout을 무엇으로 표현하는가

RFD 1의 A는 layout 트리가 멤버 추가 한 번에 평탄화되는 문제를 다룬다. 이 축은 비교 대상에서 정보가 가장 적었다 — orca·cmux·paseo 모두 pane 트리를 다루지만 자료구조를 소스에서 확인하지 못했다. 다만 orca의 persistence.ts가 6777줄이고 그 안에 ptyIdsByLeafId라는 이름이 보이는 것으로 보아, leaf ↔ pty를 별도 맵으로 유지하고 layout 트리 자체는 보존하는 방향으로 읽힌다.

orca/src/main/persistence.ts:6777// Why: first tab spawn — persist a minimal layout so a SIGKILL before the
// renderer snapshot can't lose ptyIdsByLeafId.

이 주석이 시사하는 바가 있다. orca는 렌더러 스냅샷이 오기 전에 SIGKILL을 맞는 창을 알고 있고, 그 창에서 잃는 것이 무엇인지(leaf→pty 매핑) 정확히 지목한다. ttym이 이번에 shutdown 저장 순서를 뒤집은 것(2a3e695)과 같은 종류의 방어다.

6. building block 관점에서의 재해석

이 절은 "tmux처럼 범용적이고 pluggable·customizable한 building block을 만들고, 웹·네이티브 클라이언트가 그 위의 가장 좋은 소비자가 된다"는 방향을 전제로 앞의 분석을 다시 읽은 것이다. 앞 절들은 이 전제 없이 작성했다.

6.1 이 방향에서 각 프로젝트가 놓이는 자리

building block                    소비자를 겸함                  완성품
──────────────────────────────────────────────────────────────────────────
abduco    최소 detach              tmux    자체 클라이언트만      orca   ADE
conmon    컨테이너 부품            paseo   데몬+프로토콜+앱       cmux   macOS 앱
                                  vibetunnel  서버+웹+앱
                                  ttym    ?

tmux가 building block으로 기능하는 이유는 클라이언트가 우수해서가 아니다. 클라이언트가 아니라 명령·훅·format 문자열이라는 조작 표면이 안정적이기 때문이다. claude-squad는 tmux의 UI를 쓰지 않는다 — tmux new-session -d를 호출하고 결과를 자기 TUI로 보여준다. 즉 tmux는 headless로 쓸 수 있어서 building block이 됐다.

이 기준을 ttym에 적용하면 위치가 분명해진다. ttym은 이미 HTTP API와 WS 프로토콜로 headless 조작이 가능하고, CLI가 그것의 첫 소비자다. 구조는 이미 building block에 가깝다. 부족한 것은 조작 표면의 안정성과 확장 지점이다.

6.2 이 방향에서 다시 보이는 것들

(1) holder를 "그 위에서 구축 가능하게" 한다는 목표는 지금 구조와 충돌하지 않는다

holder는 이미 독립 실행 파일이고, 프로토콜은 5바이트 헤더 + cmd + payload로 단순하며, 문서화만 하면 제3자가 다른 holder를 구현할 수 있다. conmon이 정확히 그 자리에 있는 물건이다. 다만 지금 프로토콜에는 두 가지가 빠져 있다 — 버전 협상과 capability 교환. 서버가 v3인데 holder가 v2인 상황(Phase 5에서 실제로 발생한다)을 프로토콜이 알 방법이 없다.

이 방향에서 우선순위가 올라가는 것. H_CMD_STATE에 protocolVersion과 capabilities[]를 추가하는 것. 지금은 Phase 5의 교차 검증 항목이지만, holder를 교체 가능한 부품으로 만들려면 기반 요건이 된다. paseo가 includeWrapFlags를 "client capability에 gate된다"고 적은 것이 같은 문제의식이다.

(2) 셀 그리드 vs raw 바이트 선택의 무게가 달라진다

4.2에서 제시한 세 갈래는 building block 관점에서 우열이 바뀐다.

안제품 관점building block 관점
(a) ring 확대가장 쌈. 실측상 시급하진 않음임시방편. 소비자가 크기를 알아야 함 = 누출된 추상
(b) snapshot seed + delta재료 있음. 중간 비용적합 — "상태 + revision"은 소비자가 이해하기 쉬운 계약
(c) 디스크 cast + pruneI/O 비용, 수명 관리 추가적합 — 파일이 곧 인터페이스. 제3자가 asciinema로 바로 소비 가능

(c)의 부수효과가 이 방향에서 특히 크다. 세션 출력이 표준 포맷 파일로 남으면 ttym을 거치지 않고도 재생·분석·공유가 되고, 그것 자체가 "그 위에 뭔가를 지을 수 있다"는 뜻이 된다. vibetunnel이 asciinema를 고른 것은 저장 방식의 선택이 아니라 생태계 선택이다.

(3) agent 훅은 registry로 만들어야 building block이 된다

지금 ttym의 Stop hook은 스크립트 한 개(scripts/ttym-claude-stop-hook.sh)와 meta.stopSeq 규약으로 되어 있다. agent를 하나 더 지원하려면 코드를 고쳐야 한다. paseo는 같은 것을 provider registry로 만들었다.

paseo/packages/server/src/terminal/agent-hooks/provider-registry.ts:23  [claudeAgentHookProvider.id]: claudeAgentHookProvider,
  [codexAgentHookProvider.id]: codexAgentHookProvider,
  [opencodeAgentHookProvider.id]: opencodeAgentHookProvider,

provider가 { id, events[], statusMap, settingsPatcher }를 내놓으면 코어는 그것을 설치·제거·해석만 한다. 이것이 "pluggable"의 구체적 형태다. 그리고 이 구조를 갖추면 3.5에서 지적한 결함(StopFailure 누락)이 개별 버그가 아니라 provider 정의의 누락으로 강등된다 — 고치기 훨씬 쉬워진다.

(4) 클라이언트 3개가 동시에 깨지는 문제(RFD 6.4)의 성격이 바뀐다

RFD 1은 D 단계에서 client/·native/·demo/가 전부 동작하지 않는 구간을 감수한다고 적었다. 사용자가 하나이고 클라이언트가 전부 같은 저장소에 있다는 근거였다.

그러나 building block을 지향하면 이 전제가 바로 무너진다. 제3자 소비자가 생기는 순간 "같은 커밋에서 함께 바뀐다"가 성립하지 않는다. paseo가 프로토콜을 별도 패키지(@getpaseo/protocol)로 뽑고 capability gating을 쓰는 이유가 이것이다.

귀결. 이 방향을 택한다면 RFD 7.7("호환 계층을 두지 않는 이유")을 재검토해야 한다. 그 절의 논거는 "외부 소비자는 알려진 것이 없다"였고, RFD 자신도 "외부 소비자가 확인되면 이 결정을 재검토해야 한다"고 단서를 달아 두었다. building block을 만들겠다는 것은 외부 소비자를 만들겠다는 선언이므로 그 단서의 조건이 충족된다.

6.3 이 방향에서 ttym이 실제로 앞서 있는 것

공정하게 적을 필요가 있다. 조사한 신규 프로젝트 중 서버를 죽였다 살려도 세션이 살아 있는 것을 실증한 것은 ttym뿐이다(paseo는 구조상 가능해 보이나 확인하지 못했다). orca·cmux는 명시적으로 포기했고, claude-squad는 tmux에 위임했다.

building block의 가치가 "그 위에 지어진 것이 오래 산다"는 데 있다면, 기반이 재시작을 견딘다는 성질은 그 자체로 차별점이다. tmux는 이 성질을 "서버가 죽지 않는다"는 전제로 얻었고, ttym은 "서버가 죽어도 된다"는 구조로 얻었다. 후자가 더 강한 보장이다 — 기반을 업그레이드하면서 그 위의 것을 죽이지 않을 수 있다는 뜻이기 때문이다.

· cmux·orca의 layout 자료구조가 실제로 트리를 보존하는지
· vibetunnel vt-fwd(Rust)가 ttym holder와 같은 수준의 분리인지
· claude-squad가 agent 완료를 어떻게 감지하는지
