ttym — 다음에 무엇을 할 것인가

“ttym을 building block으로 만들어 넥스트 레벨로 보내자”는 방향을 정하기 전에, 같은 자료를 넷에게 독립적으로 읽히고 반박을 받았다. 결론은 그 방향을 지금 열지 말라는 것이었다. 대신 프레이밍 논쟁보다 값진 발견이 둘 나왔다.

1. 지금까지의 경위

ttym은 웹 기반 터미널 멀티플렉서다. 구조가 3층인데, 그중 하나가 이 프로젝트의 고유 자산이다. 

[3] 클라이언트    브라우저 · CLI attach · native(Tauri) · demo
[2] 서버          Node. HTTP API + WebSocket + 세션/워크스페이스
[1] holder        Rust. PTY를 소유. 서버와 unix socket으로 통신
                  ↑ 서버와 분리된 프로세스라, 서버가 죽어도 안에서 도는
                    claude · ssh · 빌드가 살아남는다

오늘 이 성질로 프로덕션 서버를 v3로 무중단 교체했다. 15개 세션과 38개 claude 프로세스가 그대로 살아남았다. 조사한 8개 프로젝트 중 서버를 죽였다 살려도 세션이 사는 것은 ttym뿐이다 (orca·cmux는 명시적으로 포기했고, claude-squad는 tmux에 위임했다).

그 뒤 방향 질문이 나왔다. tmux처럼 범용적이고 pluggable·customizable한 building block을 만들고, 웹·네이티브 클라이언트가 그 위의 가장 좋은 소비자가 되게 한다는 구상이다. 지금 하던 v3 작업 중 새 설계에서 무효가 될 것이 있으니, 재설계에 덜 영향받는 것부터 하고 싶다는 단서가 붙었다.

2. 무엇을 물었나

브리핑 하나를 만들어 네 관점에 독립 배포했다. 각자 다른 질문을 받았고, 서로의 답을 보지 못했다.

관점받은 질문
계층holder / 서버 / 프로토콜 / 클라이언트의 책임을 어디서 자를 것인가. holder도 셀을 알아야 하는가
회의론v4를 막는 것이 임무. 과잉설계인 이유를 대라. v2 실패 조건이 지금도 갖춰져 있는가
상태지속성 저장소를 교체 가능하게 만들 값이 있는가. 임의 바이트 절단이 실제로 얼마나 중요한가
이행v3의 A·C·D를 언제 어떻게. 되돌릴 수 없게 되는 지점은 어디인가

브리핑에는 실측치를 전부 넣었다 — agent TUI의 행당 913바이트, 같은 3000행이 raw 2.7MB / 렌더된 스냅샷 571KB, 교체 시 바이트 39.6% 손실이 행 12.8% 손실로 축소된다는 것, Claude·Codex 모두 alternate screen을 쓰지 않는다는 것.

3. 결론 — v4를 열지 마라

넷 중 둘이 정면으로, 나머지 둘이 간접적으로 같은 결론에 이르렀다.

building block의 가치는 “코어와 별도로 진화하는 소비자”가 있을 때 생긴다. 지금은 그 전제가 없다.

web/native/demo/CLI가 같은 저장소에 있으므로 인터페이스 변경을 한 커밋에서 원자적으로 반영할 수 있다. 외부 소비자가 없으므로 하위 호환성을 약속할 대상도 없다.

— 회의론 리뷰

v2 실패 조건이 지금도 갖춰져 있다

과거에 v2 설계를 33일 하고 구현 0%로 3개월 방치한 전례가 있다. 회의론 리뷰는 그 조건이 지금도 살아 있다고 본다.

  • 완료 조건이 없다. “pluggable하고 applicable한 building block”은 어떤 API를 만들어도 더 일반화할 이유를 만들 수 있다
  • 축이 전부 미정이다. holder/서버 중 누가 셀을 소유할지, ring/cast/snapshot 중 무엇이 계약인지, 프로토콜/CLI/플러그인 중 무엇이 확장점인지가 동시에 열려 있다
  • 조사한 프로젝트가 요구사항을 공급하고 있다. paseo에 셀이 있고 orca에 GC가 있다는 사실은 ttym에 그것이 필요하다는 근거가 아니다
  • v3가 미완인데 다음 세대 이름이 생겼다. 완료보다 재분류가 더 보상적인 작업 흐름이다

그리고 하나가 새로 추가됐다.

AI 인력이 무제한이면 코드 생성량이 싸다. 그러나 잘못 공개한 계약의 폐기, 프로덕션 데이터 변환, 교차 버전 장애의 판단 비용은 싸지지 않는다. 구현 0% 대신 구현 80%짜리 잘못된 플랫폼을 만들 가능성이 생겼을 뿐이다.

v4를 정당화하는 판별식

회의론 리뷰가 제시한 조건. 셋이 모두 참일 때만 v4를 연다.

1. 이름과 소유자가 있는 독립 배포 소비자 또는 대체 구현이 실재하고
2. 그 요구가 안정된 CLI / HTTP 어댑터로 충족되지 않으며
3. 수직 절편을 기존 프로덕션과 dual-run 하여 무손실 롤백이 증명됐을 때

“향후 native 앱”, “언젠가 외부 사용”, “저장소를 바꿀 수도 있음”은 존재로 세지 않는다.

대신 building block의 실질은 안정된 CLI다

tmux가 building block인 이유는 플러그인 체계가 아니라, 외부 자동화가 반복해서 쓰는 안정된 명령 표면이 있기 때문이다. claude-squad는 tmux UI를 전혀 쓰지 않고 tmux new-session -d만 호출한다. 

비대화형 세션 생성 · 열거 · 조회 · 입력 · resize · 종료
스크립트가 판별 가능한 exit code와 구조화 출력
세션 ID와 주소의 안정된 의미
attach가 끊겨도 holder가 사는 lifecycle 계약
CLI와 서버의 버전 불일치 시 명시적 오류
이 계약을 검증하는 e2e 테스트

핵심 통찰. CLI를 호환성 경계로 두면 내부 프로토콜과 상태 표현은 계속 바꿀 수 있다. HTTP/WS와 holder 내부 프로토콜까지 장기 안정화할 필요가 없다. 실제 두 번째 소비자가 CLI로 해결되지 않는다고 증명될 때만 그 아래 계층을 공개한다.

4. 발견 ① — 이미 만들어 놓은 자산을 버리고 있다

상태 리뷰가 코드에서 찾았고, 직접 확인했다.

디스크 체크포인트   571 KB에 3000행    서버가 2초 idle / 30초마다 이미 쓰고 있음
holder raw ring     1 MB에 약 1100행    서버 교체 시 이것만 씀

session-manager.ts:190이 holder가 세션을 살렸으면 디스크 스냅샷을 unlink한다. 그 뒤 session.ts:302가 빈 xterm에 holder의 1MB DUMP만 재생한다. 

// Holder may have already brought this session back — keep that one.
if (this.sessions.has(snap.id)) {
  console.log(`[mgr] session=${snap.id} already alive via holder, dropping snapshot`);
  await unlink(snapPath).catch(() => {});
  continue;
}

오늘 프로덕션 교체 로그에 이 메시지가 15번 찍혔다.

둘은 결합된 게 아니라 배타적이다. 더 크고 정확한 것을 의도적으로 버리고 작은 것만 쓴다.

고치면 ring 크기 문제 자체가 사라진다. 체크포인트가 과거 3000행을 담당하고 ring은 마지막 체크포인트 이후의 짧은 공백만 담당하면 된다. 새 저장소도, 플러그인 API도, holder의 셀 에뮬레이션도 필요 없다.

필요한 변경은 additive하다.

holder에  DUMP_SINCE(offset)  추가        (구 DUMP는 유지)
체크포인트에  appliedThroughOffset  기록
체크포인트에  wrapFlags  기록            (3000행 bitset ≈ 375바이트)

복구 순서
  1. holder STATE에서 generationId · baseOffset · nextOffset 확인
  2. 같은 generation의 디스크 체크포인트를 xterm에 seed
  3. DUMP_SINCE(appliedThroughOffset) 으로 델타만 요청
  4. gap=false 일 때만 “정확 복구”로 판정

5. 발견 ② — 오늘 사고의 진짜 원인

오늘 교체 중 세션 하나(973)를 잃었다. launchd가 관리하던 서버와 수동으로 띄운 서버가 경쟁했고, 그 과정에서 원본 holder가 소켓을 잃었다. 이것을 절차 실수로 정리했는데, 계층 리뷰가 다르게 봤다.

현재는 새 접속이 기존 서버를 조용히 축출한다. 이것은 교체 가능성이 아니라 split-brain 위험이다.

— 계층 리뷰

즉 우연한 실수가 아니라 프로토콜이 허용하는 구조였다. holder는 클라이언트를 하나만 받고, 새 접속이 오면 아무 확인 없이 기존 것을 밀어낸다. 

ACQUIRE_CONTROLLER {
  serverInstanceId,
  expectedHolderIncarnation,
  takeover: true | false
}

기본 접속은 기존 controller가 있으면 실패
takeover는 명시적으로만 허용
성공 시 lease generation 발급, 이전 controller의 입력 · resize는 fencing

holder가 멀티클라이언트를 알아야 한다는 뜻이 아니다. 하나의 controller만 허용하되, 축출을 명시적이고 fencing 가능한 동작으로 만들면 된다.

6. 나머지 판단들

holder는 셀을 몰라야 한다 (계층·상태 리뷰가 독립 수렴)

mosh처럼 holder가 터미널 에뮬레이션을 하면 얻는 것이 분명하다. 그러나 대가가 더 크다.

  • 대체 holder가 wide character · combining mark · OSC 8 · synchronized output · reflow까지 구현해야 한다 — 교체 가능성이 오히려 줄어든다
  • 브라우저는 계속 xterm을 쓴다. Rust 셀 결과와 xterm 렌더가 갈리면 어느 쪽이 정답인지 정해야 한다
  • holder는 41일씩 산다. 구형 holder마다 다른 parser dialect가 살아남는다
  • 100열 × 3000행 = 30만 셀. 셀당 16바이트만 잡아도 4.8MB로, 현재 560KB~1.2MB의 한 자릿수 이상

재검토 조건: “서버가 무기한 내려가 있고 출력은 계속 발생해도, 고정된 저장 한도 안에서 정확한 최신 화면과 스크롤백을 반드시 복구해야 한다” — 지금 이 요구는 없다.

저장소 플러그인화 반대

ring · cast · 셀 스냅샷은 대체재가 아니라 목적이 다르다.

요소역할권위
holder raw ring서버 중단 구간을 메우는 복구 로그임시
서버 headless xterm현재 렌더링된 셀 상태런타임 권위
디스크 checkpoint셀 상태의 영속 체크포인트영속
asciinema cast선택적 녹화 · 재생복구에 쓰지 않음

플러그인 인터페이스를 만들면 단순한 load/save가 아니라 atomic checkpoint · offset 연속성 · generation 검증 · GC · 포맷 마이그레이션 · 부분 손상 처리까지 계약해야 한다. 구현체가 하나뿐인데 계약을 먼저 고정하면 내부를 개선할 때마다 호환성이 발목을 잡는다.

임의 절단 — 손실량이 아니라 침묵이 문제

측정상 손실은 작다(바이트 39.6% → 행 12.8%). 그럼에도 임의 절단을 유지하면 안 되는 이유는 깨졌다는 사실을 알 수 없다는 것이다. UTF-8 continuation, CSI/OSC/DCS 중간, hyperlink payload 중간에서 잘리면 영향이 여러 행으로 번질 수 있다. 

정확한 checkpoint offset + 연속 delta      ← 목표
  > parser-ground 의미 경계
  > screen-clear 경계                       vibetunnel
  > UTF-8 경계                              orca
  > 임의 바이트                             ttym 현재

vibetunnel의 screen-clear 경계도 완전하지 않다 — ED 2/ED 3은 SGR·cursor mode·scroll region·charset을 초기화하지 않는다. 정상 경로에서는 절단 위치를 찾지 말고 체크포인트 offset부터 이어야 한다. 안전 anchor 탐색은 overflow fallback에서만.

A를 쪼개라 (이행 리뷰)

A-1 트리 평탄화 버그 수정순수 연산 교체즉시폐기 확률 15%
A-2 소속 모델 변경members[] → layout leaf보류v4가 버릴 가능성 높음

A-1의 시급성은 실증된다. 프로덕션 workspace 7개가 전부 평탄하고 전부 균등 분할이다. 

mini                0.33/0.33/0.33      tooling      0.5/0.5
workspace 3~7       전부 균등            중첩 깊이 1 이하: 7/7

sessionIdsToLayout이 만드는 정확한 형태다. 우연히 전부 균등값이 되기는 어렵다. 과거 세션에 split UI를 실제로 쓴 기록이 있으므로, 만들었다가 잃은 것으로 읽힌다.

A-2가 위험한 이유. “workspace 소속 세션은 반드시 pane에 보인다”를 불변식으로 승격하면 배치 없는 세션 · 클라이언트별 뷰 · 최소화 상태가 전부 닫힌다. headless building block을 지향하면서 headless 세션을 금지하는 셈이다.

A-2 전에 답해야 할 네 질문 — 하나라도 미확정이면 저장 포맷을 바꾸지 않는다.

세션과 workspace의 cardinality가 정말 항상 1:N인가?
workspace 소속 세션은 반드시 layout leaf여야 하는가?
layout은 서버 전역 문서인가, 클라이언트별 view인가?
name · role · tags는 session 속성인가, membership 속성인가?

D는 rollout layer이지 선행 조건이 아니다

세 클라이언트가 동시에 깨지는 구간은 받아들일 조건이 아니라 설계 결함이다.

— 이행 리뷰

서버는 이미 HTTP와 WS 양쪽으로 세션 lifecycle을 지원한다. 동시에 깨뜨릴 기술적 이유가 없다. expand → migrate → contract로 하면 그 구간을 만들 필요가 없다. 

D-transport   공용 client adapter, HTTP lifecycle로 하나씩 이전      지금 가능
D-semantic    주소 문법 · new/split · remove/detach/terminate 구분   소속 모델 확정 후
              지금 시작하면 폐기 확률 65%

되돌릴 수 없게 되는 지점의 재정의

변환기를 실행하는 순간이 아니라, v3로 표현할 수 없는 첫 v4 전용 mutation을 프로덕션에 기록하는 순간이다.

— 이행 리뷰

그 전까지는 shadow projection으로 새 형태를 병행 검증할 수 있다.

7. 교정된 것

카운슬을 돌리기 전에 내가 적어둔 잠정 결론과 대조했다.

내 주장교정
“A를 미루자”A-1(트리 버그)은 즉시, A-2(소속 모델)만 보류
“holder 프로토콜 버전 협상이 첫 작업”소비자가 없다. 필요한 건 controller lease와 checkpoint offset
“D를 앞으로 당기자”D-transport만. D-semantic은 지금 하면 폐기 확률 65%
“v4는 계층 계약 확립”계약은 CLI 하나면 된다. 계층 전체가 아니라
“체크포인트를 holder에 맡기자”디스크에 이미 있다. 버리지만 말면 된다

살아남은 것은 “재설계에 영향 덜 받는 것부터”라는 기준 자체다. 이행 리뷰가 이를 작업별 폐기 확률로 정량화했고, 네 리뷰 모두 그 기준을 지지한다.

8. 실행 순서

Tier 1 — 지금. 실증된 결함이고 어느 설계에서도 남는다
  1. A-1 트리 평탄화 수정 폐기 15%
    프로덕션 7/7 손상 실측. 중첩 subtree와 sizes 보존 테스트를 함께 넣는다
  2. controller lease 폐기 낮음
    오늘 973 상실의 근본 원인. 축출을 명시적 · fencing 가능하게
  3. checkpoint + delta 복구 폐기 낮음
    이미 있는 571KB 자산을 버리는 중. DUMP_SINCE 추가 + wrapFlags 기록
  4. reconcile을 삭제기에서 검증기로 폐기 20%
    지금은 layout에 없는 멤버의 이름 · role을 조용히 버린다
Tier 2 — 곧. 소유권 분리이며 URL보다 타입이 먼저
  1. C 내부 타입 분리 폐기 10% — RuntimeState · Annotations · InteractionState
  2. C additive endpoint 폐기 20% — /meta는 호환 어댑터로 유지
  3. 프로덕션 fixture 고정 폐기 5% — 실제 데이터의 비식별 복사본으로 재기동 · 롤백 테스트
Tier 3 — 소속 모델 ADR 이후
  1. 소속 모델 ADR 폐기 10% — §6의 네 질문만. 프로덕션 포맷은 아직 안 건드림
  2. D-transport 폐기 20%
  3. shadow projection 검증 폐기 25%
  4. D-semantic 폐기 20% — ADR 전 착수 시 65%

holder 셀 에뮬레이션      요구가 아직 없다

전면 재설계 / v4 트랙     판별식 미충족

Tier 1의 셋을 하면 layout 손실이 멈추고, split-brain이 막히고, 교체 복구가 1MB raw ring이 아니라 571KB 체크포인트 기준으로 올라간다. 플랫폼화보다 이쪽이 실질적인 “넥스트 레벨”이라는 것이 네 리뷰의 공통 답이다.
