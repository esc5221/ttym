ttym v2 — CLI / API 재설계 제안

설계안 완성본 · 2026-04-19 · 병렬 리뷰어 3명 합의 (framework-language · rest-resources · user-workflow) · 대상 버전 ttym > v1 (현 master @ 41f7c62)
핵심 메시지. ttym v1은 workspace가 너무 많이 이고, attach가 너무 많이 삼켰다. v2의 축은 세 가지로 요약된다. (a) member를 session에서 분리해 stable ID를 주고, (b) 자주 쓰는 상호작용(attach/open/send/await/screen)을 top-level 동사로 승격하며, (c) API를 3-plane(HTTP 제어 / SSE 관찰 / WS 터미널 IO)으로 분리한다. 이 세 축만 지키면 현재 드러난 10여 개의 냄새가 구조적으로 사라진다.

§1. 리소스 모델 — 명사 계층을 먼저 확정

현재 구현에서 member의 식별자가 sessionId라는 점이 가장 큰 구조 부채다. 멤버를 detach 후 다시 attach하면 새 sessionId가 생기는데, 그 사이 pane placement·이름·role을 누가 들고 있을지 애매해진다. v2는 member를 1급 리소스로 승격하고 session은 옆에 매달리는 binding으로 모델링한다. 
project (lightweight, derived)
└── workspace  [workspaceId]
    ├── layout (versioned document)
    │   └── pane tree
    │       ├── pane ─► memberId            (NEW: sessionId 아니다)
    │       └── split ─► children[]
    ├── members[]
    │   └── member  [memberId]              (NEW: stable, session과 별개)
    │       ├── identity  {name, role, labels}
    │       ├── binding   0..1 ─► session   (지금 붙어있는 PTY)
    │       ├── lastSessionId?              (재바인딩용 힌트)
    │       └── presence  {attached|detached|missing}
    └── events (SSE)

session  [sessionId]                        (독립 프로세스 리소스)
├── spec     {command, cwd, terminalProfile}
├── runtime  (system-owned, read-only)      ← 기존 meta 시스템 키
│   ├── terminal  {cols, rows, lastSeq}
│   ├── process   {pid, state, exitCode}
│   └── agent     {kind, externalSessionId, activeInteractionId}
├── annotations  (user-owned, patchable)    ← 기존 meta 유저 키
├── snapshot  (현재 화면)
└── interactions[]                          (NEW: await의 1급 리소스화)
    └── interaction  [interactionId]
        ├── input     {text, encoding}
        ├── submit    {mode, profile}
        ├── completion{strategy, timeoutMs}
        └── result    {completed|timed_out|failed, snapshot}

7개의 변경점

변경이유 / 효과
member.id ≠ session.iddetach/rebind 사이에도 pane·이름·role이 손상되지 않는다. federation/recording이 붙을 때 확장성↑
session은 workspace 밖에서도 존재ad-hoc 세션, 여러 워크스페이스가 같은 PTY를 관전하는 시나리오를 깨끗하게 허용한다
meta → runtime + annotations 분리시스템 키(seq/stopSeq/claudeSessionId)와 유저 라벨이 같은 네임스페이스에 충돌하지 않는다
interaction 리소스await이 "meta.seq bump + polling"에서 벗어나 서버가 상태기계를 소유한다. 브라우저에서도 await 가능
layout은 versioned documentPATCH/PUT에 If-Match. 다중 클라이언트 lost update 방지
project는 derived빈 프로젝트 유령 리소스를 만들지 않는다. workspace가 project 필드를 들고, projects는 집계 뷰
agent는 session.runtime.agent의 속성member 레벨의 에이전트 특수 분기가 사라진다. "이 세션의 런타임 특성"으로 통일

§2. CLI 언어 — 동사 / 명사 / 주소

2.1 Command tree (완성형)

ttym
├─ help  [topic]                              # attach | address | keys | member | workspace
├─ whoami                                     # canonical FQA 출력 (구: current)
├─ ls  [workspaces|members|sessions] [scope]  # tmux ls / docker ps 위치
├─ pick                                       # picker를 first-class로 (구: attach 내부 C-b s)
│
├─ attach   <target>  [--mode control|view] [--prefix C-b]   # TTY transport
├─ open     <target>  [--mode control|view] [--print-url]    # web transport
├─ send     <target>  -- <text>                              # 에이전트 인지 submit
├─ await    <target>  [--timeout ms] [-o plain|json|raw] -- <prompt>
├─ screen   <target>  [--raw] [-o ...]
├─ spawn    <agent|cmd> [--into <workspace>] [--ask '...']   # 원샷 ad-hoc
├─ next / prev                          # attach 내부와 동일 의미의 CLI 명령
│
├─ server     { start | stop | restart | status | logs [-f] }
├─ project    { ls | show | rename | delete | use }
├─ workspace  { ls | show | create | rename | delete | use | split }
├─ member     { ls | show | add | rename | detach | kill }
├─ session    { ls | show | new | kill | attach | meta }        # meta는 디버그용, 숨김
└─ agent      { ls | install | uninstall | show | resume }
읽는 법. 상위 14개는 top-level 동사(사용자가 "무엇을 하려는가"). 그 아래 6개 명사(server/project/workspace/member/session/agent)는 수명주기·구조 변경용. status는 top-level에서 내렸고, hook alias는 제거한다.

2.2 FQA — fully-qualified address

project     gpai
workspace   gpai/monorepo
member      gpai/monorepo:lead                       (슬래시 둘 + 콜론)
session     #42                                       (# prefix = raw PTY)
remote      @prod/gpai/monorepo:lead                 (미래 federation용, 현재 미사용)

축약 규칙 (context 있을 때만)
─────────────────────────────────────────────────
.           → current workspace
:lead       → current workspace 의 member lead
monorepo:lead  → current project 의 workspace 안 member
#42         → raw session (workspace 바깥도 가능)
왜 슬래시가 아니라 콜론인가. v1은 project/workspace/member 세 단을 모두 슬래시로 썼다. 결과적으로 a/b가 "project/workspace"인지 "workspace/member"인지 문맥에 따라 바뀌는 slash-depth ambiguity가 생긴다. colon은 "멤버는 워크스페이스 안의 잎(leaf)"이라는 의미를 시각적으로 분리한다. kubectl의 ns/pod, docker의 image:tag와 같은 발상이다.

2.3 attach / open — transport × mode 직교

transportmode = controlmode = view설명
attach (TTY)readwrite (기본)readonlynative 터미널에 raw 바이트 pass-through
open (web)readwrite (기본)관전 / 회의브라우저 URL 프린트 + open 호출
future mirror—collaborative여러 클라이언트 커서 가시화
제거되는 것. attach --new (attach가 provisioning까지 삼키는 숨은 부작용), --readonly (부정 플래그는 확장성 낮음, --mode=view로 대체), --cmd (POSIX -- separator로 통일).

4.2 meta 재설계 — runtime vs annotations

runtime (system)

GET /api/v2/sessions/42/runtime
{
  "terminal":  { "cols":120, "rows":40, "lastSeq":381 },
  "process":   { "pid":31042, "state":"running",
                 "exitCode":null },
  "agent":     { "kind":"claude-code",
                 "externalSessionId":"sess_…",
                 "activeInteractionId":"int_01J…" }
}
read-only. seq / stopSeq / claudeSessionId 같은 프로토콜 내부 상태는 전부 여기.

annotations (user)

PATCH /api/v2/sessions/42/annotations
{
  "labels":  ["pilot", "triage"],
  "custom":  { "ticket":"TT-142", "owner":"lullu" }
}
자유 key/value merge. 시스템 키와 절대 충돌하지 않는다.

4.3 await을 interaction 리소스로 승격

POST /api/v2/sessions/42/await
Content-Type: application/json

{
  "input":      { "text": "현재 failing test 원인만 요약해줘" },
  "submit":     { "mode": "agent-default",  "profile": "claude-code" },
  "completion": { "strategy": "agent-stop", "timeoutMs": 60000 },
  "response":   { "snapshotFormat": "plain", "includeAnsi": false }
}

─── 200 OK ──────────────────────────────────────────────────────
{
  "interaction": { "id":"int_01J…", "status":"completed",
                   "submittedAt":"…", "completedAt":"…" },
  "output": { "snapshot": { "format":"plain", "text":"원인은 …",
                            "lastSeq":381 } },
  "links":  { "session":"/api/v2/sessions/42",
              "interaction":"/api/v2/sessions/42/interactions/int_01J…" }
}

─── 202 Accepted (timeout) ──────────────────────────────────────
Location: /api/v2/sessions/42/interactions/int_01J…
{ "interaction": { "status":"timed_out" }, "links": { … } }
효과. (1) 브라우저에서도 await 가능 — 현재는 CLI 전용. (2) timeout이 에러가 아니라 "interaction이 아직 진행 중"으로 자연스럽게 이어받아진다. (3) seq bump + polling이 서버 내부로 숨어 사용자가 annotations를 실수로 덮어쓸 위험이 사라진다.

4.4 원자적 create+attach

POST /api/v2/workspaces/ws_demo/members
{
  "member":    { "name":"claude-sub", "role":"agent", "labels":["claude"] },
  "binding":   { "mode":"create",
                 "session": { "command":["claude","--dangerously-skip-permissions"],
                              "cwd":"/repo", "terminal":{"cols":120,"rows":40},
                              "agentProfile":"claude-code",
                              "readyProbe":{"kind":"first-screen","timeoutMs":5000} } },
  "placement": { "op":"split", "targetMemberId":"mem_root",
                 "direction":"right", "ratio":0.5 }
}
verify=true 는 사라진다. 대신 readyProbe가 명시 정책: none | process-alive | first-output | first-screen | custom-regex. 현재처럼 boolean에 2초 하드코딩된 마법이 사라지고, 에이전트별 부팅 속도 차이(§2.5)도 readyProbe로 표현된다.

§5. 3-Plane 아키텍처 — 책임 분리

┌──────────────────── CONTROL PLANE (HTTP JSON) ────────────────────┐
│  생성·구성·조회·의미적 요청(await).  stateless, cacheable.              │
│    POST /workspaces        PATCH /workspaces/:id/layout                 │
│    POST /sessions          POST  /sessions/:id/await                    │
│    POST /members           POST  /sessions/:id/interactions             │
└────────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────── WATCH PLANE (SSE, text/event-stream) ──────────┐
│  상태 변화 구독.  session created / agent active / member detached …    │
│    GET /api/v2/events?workspaceId=ws_demo&types=session,member,agent    │
│                                                                         │
│  event: session.state                                                   │
│  data:  {"sessionId":42,"state":"attached","lastSeq":381}               │
└────────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────── DATA PLANE (WebSocket, binary+text) ───────────┐
│  저지연 terminal IO.  프레임 스키마 고정, 버전은 subprotocol로.         │
│                                                                         │
│  Text frame  (control):                                                 │
│    {"type":"attach","sessionId":42,"fromSeq":120,"mode":"control",      │
│     "terminal":{"cols":120,"rows":40}}                                  │
│    {"type":"attached","session":{…},"lastSeq":125}                      │
│                                                                         │
│  Binary frame (bytes):                                                  │
│    [frameType:u8][sessionId:u32le][seq:u32le?][payload…]                │
│      0x01 = data_out  (seq 포함, 서버→클라)                              │
│      0x02 = data_in   (클라→서버)                                       │
│      0x03 = ack                                                         │
│      0x04 = pause_view / resume_view                                    │
└────────────────────────────────────────────────────────────────────────┘
plane책임전송누가 쓰나
ControlCRUD + 의미적 동작HTTP/1.1+JSONCLI, 브라우저 UI, 자동화 스크립트
Watch상태 변화 구독SSE브라우저 대시보드, 멀티-클라이언트 동기화
Data터미널 입출력WebSocket (subprotocol ver)xterm.js, ttym attach
v1의 증상: 상태 변화가 polling으로만 관측 가능 (agent-api.ts의 SSE는 비활성), WebSocket 하나에 HELLO / LIST / CREATE / ATTACH / DATA가 뒤섞여 있어 control과 data의 경계가 없음. v2는 WS에서 CREATE·LIST를 제거하고 HTTP로 돌려보낸다.

§6. 컨텍스트 추론 · 출력 모드

6.1 context inference — 5단계 결정 트리

1. 사용자가 명시 주소를 줬나?          예 → 그대로 사용
   (gpai/core, :lead, #42 등)        아니오 ▼

2. 지금 ttym attach 내부인가?          예 → TTYM_PROJECT / TTYM_WORKSPACE / TTYM_MEMBER 로 해석
   (TTYM_SESSION_ID 존재 확인)        아니오 ▼

3. cwd 위로 올라가며 .ttymrc 발견?     예 → 파일의 project / workspace / default_member
   (repo/팀 공용 기본값)              아니오 ▼

4. ~/.ttym/context.json (MRU) 히트?    예 → live면 그대로, dead면 다음 후보
   (cwd → 최근 workspace/member)      아니오 ▼

5. 현재 workspace의 agent member가 1개뿐? 예 → 그 멤버를 기본 타깃
                                       아니오 ▼

6. interactive TTY?                    예 → ttym pick 자동 오픈
                                       아니오 → 모호성 에러 + 후보 3개 제시
--current는 제거하지 않는다. escape hatch로 남기되 help의 default 예시에서는 뺀다. ttym whoami는 언제 어느 단계에서 추론이 성공했는지 항상 표기한다 — "context가 마법처럼 바뀌는 느낌"을 제거하는 핵심.

6.2 output modes — 단일 플래그

-o, --output {pretty|json|plain|quiet}    (기본값: stdout이 TTY면 pretty, 파이프면 plain)

pretty   사람용. 컬러, 정렬, 섹션. 터미널에서만.
json     안정 스키마. 스크립트의 기본.
plain    grep/awk용 최소 필드 (tab-separated).
quiet    stdout 없음. exit code + stderr 경고만.

환경변수 단일 스위치
  TTYM_OUTPUT=json         # 전역 (스크립트 상단에 export)
  TTYM_NO_COLOR=1

6.3 에러 메시지 스타일 — "무엇 → 왜 → 다음 한 단계"

BEFORE:  session 42 not found
AFTER:   session 42 not found

§7. 설계 원칙 · 안티패턴

7.1 핵심 설계 원칙 10

P1한 단어는 한 효과만 가진다. detach · kill · delete · remove는 서로 다른 상태 전이여야 한다. 동의어가 되면 언어가 무너진다.
P2자주 쓰는 행위는 top-level 동사. 드문 구조 변경은 명사 아래. 토큰 길이 ∝ 빈도의 역수.
P3transport와 capability를 분리한다. attach/open은 경로이고, --mode control|view는 권한/의도다. 섞으면 안 된다.
P4주소는 한 canonical form이 있다. project/workspace:member + #id. 파서는 관대해도 문서·출력·에러는 한 형태만.
P5member는 session과 분리된 1급 리소스. stable memberId는 v2의 가장 중요한 구조 결정이다.
P6system-state와 user-state는 keyspace를 공유하지 않는다. runtime(read-only) vs annotations(patchable).
P7await은 interaction 리소스다. 서버가 상태기계를 소유한다. 브라우저에서도 가능하고, timeout은 에러가 아닌 진행 중 상태다.
P8복합 동작은 서버에서 원자적으로. create session → attach to workspace → split layout을 클라가 3번 호출하면 실패 시 일관성이 깨진다.
P9transport 별 책임 분리. HTTP = 제어, SSE = 관찰, WS = 터미널 바이트. 한 채널에 섞지 않는다.
P10컨텍스트는 도우미, 마술이 아니다. 추론 과정은 항상 whoami로 관찰 가능해야 한다. --current는 escape hatch로 남겨 신뢰를 유지한다.

7.2 피하는 안티패턴 5

  1. Flat-namespace 지옥. AWS CLI처럼 ttym workspace-send-member로 늘어나면 언어가 죽는다. 명사 × 동사 그리드를 유지한다.
  2. Slash-depth 추론 과잉. a/b가 상황에 따라 workspace인지 member인지 바뀌면 멘탈모델이 무너진다. v2는 :로 member 경계를 시각적으로 분리.
  3. attach의 숨은 provisioning. "붙는다"는 행위가 "만든다"까지 삼키면 사용자는 실패 원인을 예측 못한다. attach --new 제거.
  4. free-form meta dump. 시스템 키(seq/stopSeq)와 유저 라벨이 같은 네임스페이스면, 어느 한쪽이 조용히 손상된다.
  5. 내부 디버그 표면의 public 승격. top-level meta는 v1의 큰 실수. v2는 session meta로 격하해 안정 계약에서 뺀다.

§8. 마이그레이션 로드맵

8.1 3단계 호환 전략

Phase 1  ALIAS   (v1.x, 최소 3개월)
