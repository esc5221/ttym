1. Summary

이 문서는 ttym의 workspace/session 데이터 모델과 agent interaction 처리를 재정의한다. 변경의 중심은 둘이다. layout을 실제 트리로 다루어 workspace 소속의 단일 장부로 삼는 것, 그리고 agent 응답을 세션 버퍼 전체가 아니라 요청 단위 구간으로 반환하는 것이다. CLI 표면 정리는 이 둘에서 파생되며 마지막에 온다.

2. Motivation

2.1 layout 연산이 트리를 보존하지 않으며, 그 과정에서 세션이 소실된다

workspace의 layout은 pane과 split으로 이루어진 트리로 선언되어 있다. 그러나 appendSessionToLayout, removeSessionFromLayout, splitRight는 모두 트리를 sessionId 목록으로 평탄화한 뒤 sessionIdsToLayout으로 재구성한다. 이 함수는 항상 단일 row split과 균등 sizes를 반환한다.

server/src/workspace-store.ts:332-372 — 재현입력   split row [0.7, 0.3]
         ├ pane #1
         └ split col [0.5, 0.5]
             ├ pane #2
             └ pane #3

addMember(#4)

출력   split row [0.25, 0.25, 0.25, 0.25]
         ├ pane #1  ├ pane #2  ├ pane #3  └ pane #4

멤버를 하나 추가하는 연산이 중첩 구조와 사용자가 조정한 비율을 함께 버린다. 브라우저 UI에서 만든 배치는 CLI로 세션을 하나 추가하는 순간 사라진다. splitRight는 이름과 달리 노드를 쪼개지 않고 평탄 목록의 순서만 바꾼다.

같은 원인에서 데이터 소실이 발생한다. reconcileWorkspace는 members 배열을 layout에서 파생시킨다. layout에 없는 멤버는 개명되지 않고 제거된다.

server/src/workspace-store.ts:292-313 — 재현입력   members = [#1 "claude", #2 "claude"],  layout = pane #1
출력   members = [#1 "claude"]

#2는 이름 충돌 처리 없이 사라진다.

소속 정보의 장부가 layout과 members[] 둘이고, 한쪽이 다른 쪽을 조용히 덮어쓴다.

2.2 interaction 결과가 요청 단위로 구분되지 않는다

ttym workspace await은 agent에게 프롬프트를 보내고 응답 완료를 기다린 뒤 GET /api/sessions/:id/screen의 결과를 반환한다. 이 endpoint는 SerializeAddon.serialize()를 호출하며, 그 결과에는 뷰포트뿐 아니라 스크롤백 전체가 포함된다.

@xterm/addon-serialize 0.14 — 80x24, scrollback 3000, 100줄 기록 후 측정buffer.baseY 77,  buffer.length 101
serialize()                    line-1 포함,  line-100 포함,  892 bytes
serialize({scrollback: 3000})  동일

따라서 await의 반환값은 방금 보낸 프롬프트의 응답이 아니라 세션이 시작된 이래의 출력 전체다. 호출자는 그 안에서 이번 응답의 경계를 직접 찾아야 하며, 경계를 표시하는 정보는 제공되지 않는다. 스크립트에서 응답만 취하려면 호출 전 화면을 따로 저장해 두고 차분을 계산하는 수밖에 없다.

완료 감지는 CLI가 1초 간격으로 meta.stopSeq를 조회하는 방식이다.

bin/ttym:1321-1331const deadline = Date.now() + timeoutMs;
while (Date.now() < deadline) {
  await new Promise((r) => setTimeout(r, 1000));
  const meta = await fetchJson(port, `/api/sessions/${'{'}sessionId{'}'}/meta`);
  if (meta && String(meta.stopSeq) === nextSeq) { completed = true; break; }
}

폴링 간격이 곧 최소 지연이다. 0.2초 만에 끝나는 응답도 await은 1초 이상 걸린다. 에이전트를 병렬로 여러 개 띄우면 그 수만큼 조회가 곱해진다.

2.3 프로토콜 상태가 사용자 키스페이스에 있다

/api/sessions/:id/meta는 임의의 key/value를 병합하는 endpoint다. 동시에 await의 요청/완료 대응을 위한 seq와 stopSeq, agent 연동을 위한 claudeSessionId가 같은 평면에 저장된다. CLI가 이 키를 직접 쓴다.

bin/ttym:1308-1311const prevMeta = await fetchJson(port, `/api/sessions/${'{'}sid{'}'}/meta`);
const nextSeq = String((parseInt(prevMeta?.seq || '0', 10) || 0) + 1);
await fetchPatch(port, `/api/sessions/${'{'}sid{'}'}/meta`, { seq: nextSeq });

사용자가 ttym meta 42 --set seq=0을 실행하면 이후의 await은 stopSeq와 seq가 다시 일치할 때까지 완료를 감지하지 못한다. 문서화된 사용자 API로 프로토콜 상태를 파괴할 수 있다.

2.4 표면에 동작이 같은 이름이 있다

ttym workspace remove와 ttym workspace terminate는 같은 분기에서 처리되며 동일한 두 요청을 보낸다 — 멤버 삭제 후 세션 삭제. 관측 가능한 차이는 출력 문자열뿐이다 (bin/ttym:1265-1282). terminate는 README와 CLAUDE.md 어디에도 기술되어 있지 않다.

3. Scope

2.1~2.4는 서로 다른 층에 있다. 2.1과 2.3은 저장 모델, 2.2는 실행 모델, 2.4는 CLI 표면이다. 이 문서가 넷을 함께 다루는 이유는 하나의 원자적 변경을 제안하기 때문이 아니라, 셋이 같은 데이터 모델 위에서 정의되어야 하고 그 모델을 한 번에 서술하는 편이 짧기 때문이다.

제안은 독립적으로 병합 가능한 세 변경으로 나뉜다.

변경다루는 문제의존
A. layout을 소속의 단일 장부로2.1없음
B. interaction과 transcript2.2없음
C. runtime / annotations 분리2.3없음
D. CLI 표면 정리2.4A, B

A·B·C는 서로를 필요로 하지 않으며 각각 단독으로 검증하고 병합할 수 있다. D만 A·B에 의존한다. 배치 관련 인자의 문법이 A가 제공하는 연산에 의존하고, await의 출력 형식 인자가 B에 의존하기 때문이다. D를 먼저 하면 두 번 고치게 된다.

4. Guide-level explanation

4.1 명사

사용자가 다루는 개체는 workspace와 session 둘이다. workspace는 layout과 그 안에서 사는 session들이다. session은 PTY 하나이며 workspace 안에서 유일한 이름을 갖는다.

세션은 반드시 하나의 workspace에 속한다. 소속을 명시하지 않고 만든 세션은 default workspace가 받는다. 사용자에게 "workspace 밖 세션"이라는 상태는 존재하지 않는다.

4.2 주소

core            workspace "core"
core:claude     workspace "core" 안의 session "claude"
:claude         현재 workspace 안의 "claude"
#42             session id — 도구와 디버깅용

구분자는 콜론 하나다. project는 workspace의 선택적 라벨이며 주소의 일부가 아니다. project로 좁히려면 ttym ls --project gpai처럼 필터로 지정한다.

주소를 생략하면 다음 순서로 대상을 정한다. ttym tty 안에서 실행 중이면 $TTYM_SESSION_ID가 속한 workspace, 그렇지 않으면 ~/.ttym/context.json의 최근 사용 항목, 둘 다 해당하지 않으면 후보를 나열하고 종료한다. ttym whoami는 어느 단계에서 대상이 정해졌는지 함께 출력한다. 단계가 보이지 않으면 사용자는 잘못된 세션에 명령을 보낸 뒤에야 그 사실을 알게 된다.

4.3 세션 만들기

생성 명령은 둘이다. 배치를 신경 쓰지 않으면 new, 위치를 지정하면 split이다.

ttym new claude                       agent registry에서 "claude"를 찾아 실행
ttym new runner -- /bin/zsh           이름 runner, 명령 /bin/zsh
ttym new core:dev -- npm run dev      workspace를 주소로 지정

ttym split :claude dev -- npm run dev   :claude 오른쪽에 dev 생성
ttym split :claude dev --down --ratio 0.3

첫 인자는 이름이고 -- 뒤는 명령이다. 명령을 생략하면 이름을 agent registry에서 찾는다. 없으면 오류다. new는 위치 관련 인자를 받지 않는다. "어디에 만들 것인가"에 답해야 하는 경우가 split이다.

이 구분은 tmux의 new-window와 split-window에 대응한다.

4.4 agent에 질문하기

$ ttym await :claude -- '실패하는 테스트의 원인만 요약해줘'
원인은 tests/api.test.ts:41의 fixture가 …

$ ttym await :claude -o json -- '다음 단계 제안'
{"interaction":{"id":"int_01J…","status":"completed"},
 "transcript":"…"}

반환값은 이번 요청이 만들어낸 출력 구간이다. 이전 대화나 세션 시작 시의 배너는 포함되지 않는다. 응답 완료를 감지하는 방식은 agent의 Stop hook이며, 설치는 ttym agent install claude가 한다.

전체 화면이 필요하면 ttym screen이 현재 뷰포트를 반환한다. transcript는 요청 단위 이력이고 screen은 현재 상태다.

5. Reference-level explanation

5.1 데이터 모델

workspace
  id           서버가 생성. 변경되지 않음
  name         표시용 이름
  project?     선택적 라벨
  layout       pane tree. 잎은 sessionId
  layoutVersion  동시 편집 검출용 정수

session
  id           PTY 식별자. 서버 재시작을 넘어 보존됨
  workspaceId  소속 workspace
  name         workspace 안에서 유일
  role?        선택적 라벨
  spec         { cmd, cwd, cols, rows, scrollback }
  runtime      서버 소유, 읽기 전용
  annotations  사용자 소유, 병합 가능

세션의 이름과 role은 session이 소유한다. workspace는 members[]를 갖지 않는다. 소속 여부는 layout에 잎으로 존재하는지로 결정된다.

  1. N1. session은 정확히 하나의 workspace에 속한다.
  2. N2. session 이름은 workspace 안에서 유일하다. 중복 요청은 409로 거절한다.
  3. N3. workspace의 안정 식별자는 id다. name과 project는 변경 가능하다.
  4. N4. workspaceId와 name은 PATCH로 변경할 수 없다. move와 rename 연산으로만 바뀐다.

5.2 layout 연산

연산은 넷이다.

연산동작
split(target, dir, ratio)target pane을 split 노드로 치환하고 새 pane을 형제로 넣는다
close(target)잎을 제거한다. 형제가 하나만 남으면 부모 split을 그 형제로 대체한다
resize(node, sizes)해당 split의 sizes만 교체한다
move(session, workspace)원 workspace에서 close, 대상 workspace에 배치

모든 연산은 다음 계약을 만족한다. 대상 노드와 그 조상만 재작성하고, 형제 서브트리와 각 split의 sizes는 입력 그대로 출력에 남긴다. sessionId 목록을 경유하는 재구성은 하지 않는다. 이것이 2.1을 해결하는 전부다.

동시 편집은 layoutVersion으로 검출한다. PUT /layout과 POST /layout/ops는 요청에 담긴 버전이 현재 버전과 다르면 409를 반환한다. 브라우저에서 pane을 드래그하는 동안 CLI가 세션을 추가하는 상황이 실제로 발생한다.

5.3 interaction과 transcript

interaction은 프롬프트 하나와 그에 대응하는 출력 구간이다. 서버가 상태를 소유한다.

interaction
  id           int_…
  sessionId
  prompt
  mark         제출 시점의 버퍼 행 위치
  status       pending | completed | timed_out | failed
  transcript   완료 시 채워짐

transcript는 headless xterm 버퍼의 행 구간이다. 제출 시점에 buffer.active.baseY + buffer.active.cursorY를 mark로 기록하고, 완료 시점의 같은 값까지의 행을 읽어 문자열로 만든다.

이 방식을 쓰는 이유는 원시 바이트 구간을 자르는 방식이 TUI에서 동작하지 않기 때문이다. 에이전트는 같은 행을 반복해서 다시 그린다. 바이트 구간에는 그 중간 프레임이 모두 남지만, xterm 버퍼는 이미 최종 셀 상태로 해소한 결과를 갖고 있다.

@xterm/headless 6.0 — 제자리 redraw 3프레임 후 mark 구간 추출입력   "\r\x1b[K생각 중..."
       "\r\x1b[K생각 중...."
       "\r\x1b[K답변: 42"

추출   ["답변: 42"]

구간 추출이 이전 이력을 배제하는지도 확인했다.

80x24, scrollback 3000. 50줄 기록 후 mark, 이어서 60줄 기록mark 50,  end 110,  추출 61행
"old-50" 포함 여부   false
"resp-1"  포함 여부   true
"resp-60" 포함 여부   true

이 설계는 세션이 일반 버퍼를 쓴다는 전제에 의존한다. alternate screen buffer(\e[?1049h)를 사용하는 프로그램은 스크롤백을 남기지 않으므로 mark 구간이 뷰포트 크기를 넘지 못한다. Claude Code에 대해서는 확인했다.

claude, TERM=xterm-256color, 100x30 PTY, 15초 관측?1049h   미출현
?1047h   미출현
?47h     미출현
?2004h   출현 (bracketed paste)
?25l     출현 (cursor hide)

Claude Code는 일반 버퍼에 인라인으로 렌더링한다. Codex CLI는 아직 확인하지 않았다(§9).

완료 감지

agent의 Stop hook이 POST /api/internal/sessions/:id/stop을 호출하고, 서버가 해당 세션의 pending interaction을 완료 처리한다. POST /interactions로 대기 중인 HTTP 요청은 그 시점에 응답한다. 클라이언트 폴링은 없앤다.

POST /api/sessions/42/interactions   { prompt, timeoutMs }
  200  { interaction: { id, status: "completed" }, transcript: "…" }
  202  { interaction: { id, status: "pending" } }   + Location

GET /api/sessions/42/interactions/int_…      이어받기

timeout은 오류가 아니라 아직 완료되지 않은 상태다. 202를 받은 호출자는 Location으로 이어받는다.

제출 규약

runtime.agent.kind에 따라 결정한다. claude-code와 codex는 텍스트 전송 후 CR(0x0d)을 덧붙인다. 셸과 미상 세션은 아무것도 덧붙이지 않는다. 원시 바이트가 필요하면 POST /input이 그대로 전달한다.

5.4 runtime과 annotations

meta를 두 endpoint로 나눈다.

GET /api/sessions/42/runtime        서버 소유, 쓰기 불가
{
  "terminal": { "cols":120, "rows":40, "lastSeq":381, "mark":1204 },
  "process":  { "pid":31042, "state":"running", "exitCode":null },
  "agent":    { "kind":"claude-code", "externalSessionId":"…",
                "activeInteractionId":"int_…" }
}

GET|PATCH /api/sessions/42/annotations     사용자 소유
{ "ticket":"TT-142", "owner":"lullu" }

interaction의 상태는 어느 쪽에도 저장하지 않는다. 서버 메모리에 두고 세션 스냅샷에 함께 직렬화한다. seq와 stopSeq는 사라진다. 사용자가 쓰는 endpoint로 프로토콜 상태에 도달할 경로가 없어진다.

5.5 새로 추가되거나 의미가 바뀌는 endpoint

pathmethod비고
/api/workspacesPOSTid를 서버가 생성한다. 현재는 요청 본문이 제공한다
/api/workspaces/{wid}/layoutGET, PUTPUT은 layoutVersion 불일치 시 409
/api/workspaces/{wid}/layout/opsPOST{baseVersion, ops[]} — split · close · resize
/api/sessionsPOST생성 · 소속 · 배치를 한 요청으로 처리
/api/sessions/{sid}/movePOSTN4
/api/sessions/{sid}/renamePOSTN4. 중복이면 409
/api/sessions/{sid}/runtimeGET구 meta의 시스템 키
/api/sessions/{sid}/annotationsGET, PATCH구 meta의 사용자 키
/api/sessions/{sid}/interactionsPOST200 또는 202
/api/sessions/{sid}/interactions/{iid}GET이어받기
/api/internal/sessions/{sid}/stopPOSTStop hook 진입점

세션 생성이 한 요청이 되는 이유는 현재 클라이언트가 POST /api/sessions 후 POST /api/workspaces/:id/members를 호출하며, 두 요청 사이에서 실패하면 어느 workspace에도 속하지 않은 세션이 남기 때문이다.

5.6 변경하지 않는 것

holder 프로세스 모델은 그대로 둔다. PTY 소유권이 서버 밖에 있어 서버 재시작이 세션을 죽이지 않으며, 이 속성은 이 문서가 바꾸려는 어떤 것과도 무관하다. 변경 이유가 없고 재검증 비용이 크다.

WebSocket wire 포맷도 유지한다. sessionId는 계속 u16 리틀엔디언이다(client/src/protocol.ts:48). 정리할 것은 프레임 종류뿐이다 — CREATE, LIST, DESTROY를 제거하고 수명주기를 HTTP에 남긴다. 이는 D에 포함된다.

6. Drawbacks

6.1 transcript는 한계를 없애지 않고 옮긴다

현재 await의 출력은 스크롤백 설정값(session.ts:190, 3000행)에서 잘린다. transcript도 같은 버퍼를 읽으므로 같은 지점에서 잘린다. 달라지는 것은 잘린 결과가 "이전 이력이 섞인 전체"에서 "이번 응답의 뒷부분"으로 바뀐다는 것뿐이다. 응답 하나가 3000행을 넘으면 앞부분이 사라진다. 에이전트의 반복 redraw가 스크롤백을 얼마나 빨리 소모하는지는 측정하지 않았다(§9).

6.2 저장 형식 변환에 되돌릴 경로가 없다

workspaces.json은 version 2에서 3으로 일방향 변환된다. members[]의 name과 role을 세션 쪽으로 옮기고 나면 원래 형식으로 복원할 방법이 없다. 변환 시점에 살아 있는 holder들은 그대로 남으므로, 변환이 잘못되면 세션은 살아 있는데 소속 정보만 잃은 상태가 된다. 사용자가 한 명이라는 사실은 호환 계층을 생략할 근거는 되지만 백업을 생략할 근거는 아니다. 변환 전 원본 보존을 구현 요구사항에 포함해야 한다.

6.3 layout을 소속의 유일한 장부로 삼으면 닫히는 것이 있다

세션이 workspace에 속하려면 layout의 잎이어야 한다는 규칙은, 화면에 자리를 차지하지 않는 세션을 허용하지 않는다. detach한 세션의 자리를 비워 두는 것, 최소화 상태로 두는 것, 이름만 등록하고 나중에 배치하는 것이 모두 불가능해진다. 현재 구현이 사실상 그렇게 동작하고 있으므로 잃는 기능은 없지만, 이 문서는 그것을 규칙으로 승격시켜 향후 선택지를 좁힌다.

6.4 D는 클라이언트 세 개를 동시에 고쳐야 한다

client/, native/, demo/가 같은 API를 쓴다. D를 시작한 시점부터 셋을 모두 고칠 때까지 어느 것도 정상 동작하지 않는다. A·B·C는 이 문제가 없다. D를 마지막에 두는 이유 중 하나다.

6.5 명령 수는 줄지 않는다

현재 top-level 명령은 12개이고 제안하는 것도 12개다. 줄어드는 것은 workspace 하위에 있던 고빈도 동사가 top-level로 올라오면서 입력 토큰이 짧아지는 것과, 동작이 같은 이름(remove/terminate)이 사라지는 것이다. "명령이 단순해진다"는 주장은 개수로 뒷받침되지 않는다.

6.6 new와 split의 분리는 관례를 따르지 않는 쪽이 있다

tmux 사용자에게는 new-window/split-window와 대응하여 자연스럽다. 반면 docker run처럼 하나의 생성 동사에 옵션을 붙이는 관례에는 어긋난다. 전자를 택한 이유는 §7.3에 있다.

7. Rationale and alternatives

7.1 member를 1급 리소스로 승격하지 않는 이유

선행 설계문서(ttym-v2-design.html)는 member에 세션과 독립된 안정 식별자를 부여할 것을 제안했다. 근거는 세션이 다시 만들어질 때 배치·이름·role이 손상된다는 것이었다.

그 손상의 주된 경로는 서버 재시작 시 스냅샷을 새 id로 복원하고 layout을 사후에 remap하는 방식이었고, 이는 4b06353에서 제거되었다. 세션 id는 이제 재시작을 넘어 보존된다. 남는 경로는 세션이 죽어 새로 만들어지는 경우인데, 이는 식별자 계층을 하나 더 두는 것보다 layout의 잎을 비워 두는 방식이 더 적은 변경으로 해결한다.

또한 현재 구현은 이미 members[]를 layout의 파생물로 취급한다(2.1). member를 1급으로 올리는 것은 그 방향을 뒤집는 것이고, 뒤집을 만한 요구가 아직 관측되지 않았다.

7.2 transcript를 원시 바이트 구간으로 만들지 않는 이유

대안은 OutputRing의 seq 구간을 잘라 반환하는 것이다. 이미 seq 기반 delta replay가 구현되어 있으므로 추가 상태가 거의 필요 없다.

그러나 반환값이 사용 불가능하다. 에이전트 TUI는 같은 행을 반복해서 다시 그리므로 바이트 구간에는 중간 프레임이 모두 포함된다. 5.3의 재현에서 3프레임 redraw는 xterm 버퍼로는 ["답변: 42"] 한 행이지만, 바이트 구간으로는 세 프레임과 소거 시퀀스가 모두 남는다. ANSI를 제거해도 생각 중...생각 중....답변: 42가 된다.

7.3 배치를 new의 옵션이 아니라 split으로 분리한 이유

대안은 ttym new <name> [--right-of X] [--ratio R] [--in W] [--no-attach] …다. 생성 동사가 하나이므로 배우기 쉽다는 장점이 있다.

이 방향의 문제는 옵션이 단조 증가한다는 것이다. 선행 설계에서 new의 옵션은 6개에서 8개로 늘었고, 각 옵션은 개별적으로는 타당했다. 동사를 나누면 각 동사의 인자 수가 고정된다. new는 배치를 모르고, split은 항상 대상을 받는다. 비용은 배울 동사가 하나 늘어나는 것이고, tmux 사용자에게는 그 하나가 이미 익숙하다.

7.4 SSE 이벤트 스트림을 포함하지 않는 이유

선행 설계는 15종의 이벤트 카탈로그와 SSE endpoint를 제안했다. 현재 폴링이 존재하는 곳은 await의 완료 감지와 demo 대시보드 둘이다. 전자는 B가 Stop hook 직결로 제거하고, 후자는 5초 간격으로 낮춘 뒤 문제가 관측되지 않았다. 남은 통증이 없는 상태에서 이벤트 계약을 먼저 정의하면, 실제 소비자가 생겼을 때 다시 정의하게 될 가능성이 높다.

7.5 WebSocket sessionId를 u32로 넓히지 않는 이유

선행 설계는 u32LE를 명시했으나 현재 구현은 u16이다(protocol.ts:48). 넓히면 클라이언트 세 개의 인코더/디코더를 동시에 바꿔야 한다. 얻는 것은 동시 세션 상한 65535의 해제이고, 그 상한에 근접한 관측은 없다.

7.6 아무것도 하지 않는 경우

2.1은 배치를 저장하는 기능이 사실상 없다는 뜻이므로, UI에서 pane을 나누는 작업은 세션을 하나 추가할 때마다 다시 해야 한다. 2.2는 await을 스크립트에서 쓰려면 호출자가 매번 화면 차분을 직접 계산해야 한다는 뜻이다. 두 제약 모두 회피 가능하지만, 회피 코드가 호출자 쪽에 중복해서 쌓인다.

7.7 호환 계층을 두지 않는 이유

선행 설계는 alias 3개월, 경고 3개월, 제거의 3단계를 제안했다. 이 저장소의 클라이언트는 client/, native/, demo/이며 모두 같은 커밋에서 함께 바뀐다. 외부 소비자는 알려진 것이 없다. 단계별 호환 계층은 유지 비용만 발생시킨다. 외부 소비자가 확인되면 이 결정을 재검토해야 한다.

8. Prior art

tmux — 명사 계층(session > window > pane)과 prefix 키 체계. 이 문서는 window에 해당하는 층을 두지 않는다. workspace가 이미 그 역할을 하고, 층을 하나 더 두면 대상을 지정할 때 어느 층인지 매번 판단해야 한다. 동사 이름과 키 바인딩은 가능한 한 그대로 따른다.

conmon (CRI-O의 container monitor) — 오케스트레이터가 죽어도 컨테이너 프로세스가 살아남도록 감시 프로세스를 분리하는 구조. ttym의 holder가 같은 형태이며, PTY 수준의 detach라는 점에서는 dtach(2004)의 계보에 있다. 이 구조는 변경하지 않는다.

웹 transport는 ttyd, 다중 pane layout의 조작 문법은 zellij를 참고했다. -o json과 동사 · 명사 조합은 kubectl의 형태를 따른다.

9. Unresolved questions

  1. "응답"의 경계 정의. 에이전트가 도중에 도구를 호출하고 중간 출력을 내보내는 경우, transcript는 그 전부를 포함한다. 사용자가 원하는 것이 마지막 메시지만인 경우가 있는지, 있다면 서버가 그것을 구분할 수 있는지 확인되지 않았다. 이 답에 따라 -o에 형식이 하나 더 필요할 수 있다.
  2. 스크롤백 소요량. 6.1의 한계가 실제로 도달 가능한지 측정하지 않았다. 긴 응답 한 번이 3000행을 얼마나 소모하는지, 기본값을 올려야 하는지 판단할 데이터가 없다.
  3. Codex CLI의 화면 모드. Claude Code는 alternate screen을 쓰지 않음을 확인했으나(5.3), Codex는 확인하지 않았다. 쓴다면 그 세션의 transcript는 뷰포트 크기를 넘지 못하며, 5.3의 설계가 agent 종류에 따라 다르게 동작한다는 뜻이 된다.
  4. 복원된 세션의 mark. 재시작 복원은 seedSnapshot으로 버퍼를 채운다(session.ts:421). 이때 baseY가 복원 전 값과 어떻게 대응하는지, 복원 시점에 pending이던 interaction의 mark를 그대로 쓸 수 있는지 확인하지 않았다.
  5. 변환 검증 방법. 6.2의 저장 형식 변환을 실제 데이터로 검증할 방법이 정해지지 않았다. 변환 전후 비교 대상을 무엇으로 삼을지 정해야 한다.

10. Staging

§3의 A·B·C·D는 각각 독립된 변경으로 병합한다. A·B·C는 서로 순서가 없다. D는 A·B 이후다.

각 변경의 완료 판정은 다음과 같다.

변경판정
A중첩 layout에 세션을 추가·제거해도 형제 서브트리와 sizes가 입력과 동일하다
B이전 대화가 있는 세션에 대한 await 반환값이 이번 요청의 출력만 포함한다
Cannotations에 임의의 키를 쓴 뒤에도 await이 정상 완료한다
D클라이언트 세 개가 같은 workspace를 열었을 때 layout이 어긋나지 않는다

작업 항목의 분해와 순서는 이 문서의 범위가 아니다. §9의 1·2·3은 B의 설계에 영향을 주므로 B 착수 전에 해소해야 한다.

근거로 인용한 재현 결과는 server/src/workspace-store.ts에 대한 단위 테스트, @xterm/headless 6.0과 @xterm/addon-serialize 0.14에 대한 직접 실행, 그리고 claude를 PTY에서 실행해 얻은 바이트 관측으로 확인했다. 파일과 줄 번호는 8c3cb6c 기준이다.
