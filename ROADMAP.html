Phase A — 결함 닫기 전부 실증된 손상이다. 어느 설계에서도 남는 수정이므로 지금 한다.

A1✓레이아웃 트리를 보존한다폐기 15%

멤버를 하나 추가할 때마다 중첩 구조와 사용자가 조정한 비율이 사라진다. append·remove·splitRight가 전부 트리를 세션 ID 목록으로 평탄화한 뒤 sessionIdsToLayout으로 재구성하는데, 이 함수는 항상 단일 row split과 균등 sizes를 만든다.

이미 손상됐다. 프로덕션 workspace 7개가 전부 평탄하고 전부 균등 분할이다.

mini 0.33/0.33/0.33 · tooling 0.5/0.5 · workspace 3~7 전부 균등
중첩 깊이 1 이하: 7/7

우연히 전부 균등값이 되기는 어렵다. 과거 세션에 split UI를 쓴 기록이 있으므로 만들었다가 잃은 것으로 읽힌다.

건드리는 곳
server/src/workspace-store.ts:332-372   sessionIdsToLayout 경유 제거
shared/src/workspace-domain.ts          트리 연산이 여기로 가야 하는지 판단
구현

재귀적 tree rewrite로 바꾼다. 대상 노드와 그 조상만 재작성하고, 형제 서브트리와 각 split의 sizes는 입력 그대로 출력에 남긴다. 제거되는 child의 size만 빼고 나머지는 명시된 규칙으로 정규화한다.

완료 판정

중첩 layout(row 0.7/0.3 + 안쪽 col 0.5/0.5)에 세션을 추가·제거해도 형제 서브트리와 sizes가 입력과 동일하다. 테스트로 고정한다.

여기서 멈춘다. 소속 모델 변경(members[] → layout leaf)은 하지 않는다. 저장 포맷도 v2 그대로 둔다. 그건 D1 이후다.

A2✓controller lease — 조용한 축출을 막는다폐기 낮음

holder는 클라이언트를 하나만 받는다. 새 접속이 오면 아무 확인 없이 기존 것을 밀어낸다 (holder/src/main.rs:416). 교체 중 서버가 둘이 되면 나중에 붙은 쪽이 세션을 가져가고, 포트를 잡은 쪽은 세션을 잃는다.

오늘 실제로 물렸다. launchd가 관리하던 서버와 수동으로 띄운 서버가 경쟁해 세션 973을 잃었다. 절차 실수로 정리했지만, 계층 리뷰는 이를 프로토콜이 허용하는 split-brain으로 봤다.

건드리는 곳
holder/src/main.rs         accept 루프 + 새 프레임
server/src/session.ts      connectHolder 핸드셰이크
구현
ACQUIRE_CONTROLLER {
  serverInstanceId,          서버 인스턴스 식별
  expectedHolderIncarnation, stale manifest 방어
  takeover: true | false
}

기본 접속  기존 controller가 있으면 실패
takeover   명시적으로만. 성공 시 lease generation 발급
fencing    이전 controller의 입력·resize는 거부

구 서버는 이 프레임을 보내지 않으므로, 프레임이 없으면 기존 동작(무조건 축출)으로 폴백해 하위호환을 유지한다.

완료 판정

서버 둘을 동시에 띄우면 두 번째가 takeover 없이는 붙지 못한다. takeover: true면 붙고, 첫 번째의 입력이 거부된다.

A3✓체크포인트로 복구한다 — 버리던 자산 회수폐기 낮음

서버는 세션마다 렌더된 ANSI 스냅샷을 2초 idle / 30초마다 디스크에 쓴다. 그런데 교체할 때 holder가 살아 있으면 그 스냅샷을 지우고 holder의 raw ring만 재생한다.

디스크 체크포인트   571 KB에 3000행     이미 쓰고 있음
holder raw ring     1 MB에 약 1100행    교체 시 이것만 씀

둘은 결합된 게 아니라 배타적이다. 더 크고 정확한 것을 의도적으로 버린다. session-manager.ts:190의 dropping snapshot 로그가 오늘 교체 때 15번 찍혔다.

고치면 ring 크기 문제 자체가 사라진다. 체크포인트가 과거를 담당하고 ring은 마지막 체크포인트 이후의 짧은 공백만 담당하면 된다.

건드리는 곳
holder/src/main.rs              DUMP_SINCE(offset) 추가 (구 DUMP 유지)
server/src/session-manager.ts   :188 스냅샷 삭제 로직, persistSession
server/src/session.ts           :302 recover 경로
구현
holder    출력에 u64 byteOffset과 generationId 부여
          STATE에 baseOffset · nextOffset 보고
          DUMP_SINCE(offset) → { baseOffset, endOffset, gap, data }

체크포인트 appliedThroughOffset · holderGenerationId · cols/rows
          wrapFlags (3000행 bitset ≈ 375바이트)
          emulator 이름·버전, checksum

복구 순서  1. holder STATE 읽기
          2. 같은 generation의 체크포인트를 xterm에 seed
          3. DUMP_SINCE(appliedThroughOffset)로 델타만
          4. gap=false 일 때만 "정확 복구"로 판정
완료 판정

agent 세션을 3000행까지 채운 뒤 교체했을 때, 복구된 버퍼가 교체 전과 같은 행 수를 갖는다. ring을 축소해 강제로 넘치게 하면 gap=true로 degraded가 보고된다.

부수 효과. 정상 경로에서 임의 바이트 절단이 사라진다. 지금은 UTF-8 경계도 ANSI 시퀀스 경계도 무시하고 자르는데, 손실량보다 깨졌다는 사실을 알 수 없다는 게 문제였다. 체크포인트 offset부터 이으면 그 문제가 없다.

A4✓reconcile을 삭제기에서 검증기로폐기 20%

reconcileWorkspace()가 로드와 갱신 때마다 members[]를 layout에서 다시 만든다. layout에 없는 멤버는 이름과 role째로 조용히 사라진다.

입력  members = [#1 "claude", #2 "claude"],  layout = pane #1
출력  members = [#1 "claude"]                  ← #2는 충돌 처리 없이 삭제
건드리는 곳
server/src/workspace-store.ts:292-313
구현

불일치를 자동으로 "복구"하지 말고 진단 결과를 남긴다. mutation은 members[]와 layout을 한 연산 안에서 함께 갱신한다.

완료 판정

layout에 없는 멤버가 있으면 삭제하지 않고 경고 로그와 진단 필드를 남긴다. 정상 mutation 경로에서는 불일치가 발생하지 않는다.

Phase B — 패키지 경계와 이름 A가 끝난 뒤. 지금의 중복과 이름 불일치를 정리한다. 미래의 외부 소비자가 아니라 지금의 손유지가 근거다.

현재 상태에서 확인한 것

B1✓@ttym/protocol 신설 — wire 계약 한 벌로폐기 10%

server/src/protocol.ts와 client/src/protocol.ts가 같은 프레임 포맷을 각자 구현한다. 차이는 Buffer 대 Uint8Array뿐인데 83줄이 갈라져 있다. 한쪽만 고치면 조용히 어긋난다.

구현

Uint8Array를 공통 타입으로 삼는다. Node의 Buffer는 Uint8Array의 하위 타입이라 서버에서 그대로 통한다. 세션 ID는 현재 u16이며, 넓히지 않는다 — 그건 표면 변경이고 근거가 없다.

packages/protocol/
  src/frame.ts     encode · decode · encodeData · decodeDataFrame
  src/types.ts     CMD · DecodedFrame
  src/holder.ts    holder wire 상수 (server 전용, 트리 셰이킹으로 분리)
완료 판정

server와 client가 같은 모듈을 import하고, protocol.ts 사본이 0개다. 인코딩 왕복 테스트가 양쪽에서 같은 바이트를 낸다.

B2✓shared/ 를 @ttym/shared 패키지로 승격폐기 10%

shared/src/workspace-domain.ts가 이미 세 곳에서 쓰이는데, package.json이 없어 ../../shared/src/workspace-domain 같은 상대경로로 import된다. tsconfig의 include로 억지로 끌어오는 구조다.

demo/src/App.tsx:15        '../../shared/src/workspace-domain'
native/src/App.tsx:9        '../../shared/src/workspace-domain'
native/src/lib/api.ts:6     '../../../shared/src/workspace-domain'
구현

package.json을 주고 pnpm workspace에 등록한다. A1에서 만든 트리 연산도 여기로 모아 서버와 클라이언트가 같은 구현을 쓰게 한다 — layout 규칙이 두 곳에 있으면 다시 갈라진다.

완료 판정

상대경로 import가 0개다. @ttym/shared의 테스트가 워크스페이스 테스트에 포함된다.

B3✓@ttym/api 신설 — 두 앱이 같은 호출을 쓴다폐기 15%

native/src/lib/api.ts가 listSessions·listWorkspaces· createWorkspace·updateWorkspace·splitWorkspace를 이미 감쌌다. 반면 web(현 demo)은 같은 엔드포인트를 fetch로 직접 호출한다 — 12곳.

구현

native/src/lib/api.ts를 packages/api로 옮기고 web의 인라인 fetch를 전부 이 함수들로 교체한다. B1의 타입을 재사용한다.

packages/api/
  src/sessions.ts      list · create · destroy · screen · send · resize
  src/workspaces.ts    list · create · update · split · members
  src/interactions.ts  submit · resume        (B 단계에서 만든 것)
  src/transport.ts     baseUrl 결정, 에러 정규화

여기까지만 공유한다. 화면 구성은 각자 둔다 — web은 라우팅 기반 다중 페이지, desktop은 단일 창이다. 구조가 다른 둘을 억지로 합치면 양쪽 다 불편해진다. 공유는 API · 도메인 · 터미널 컴포넌트까지다.

완료 판정

web과 desktop 어디에도 fetch('/api/...')가 직접 나타나지 않는다. 엔드포인트를 하나 바꾸면 두 앱이 함께 따라온다.

B4✓이름 재정렬 — 결을 맞춘다폐기 5%

demo는 실체와 이름이 어긋난다. 라우팅과 다섯 페이지를 가진 실제 웹 앱인데 이름은 예제처럼 읽힌다. native는 플랫폼을 가리키고 demo는 용도를 가리켜 결도 안 맞는다.

완료 판정

B5✓@ttym/cli 승격 — 호환 경계를 패키지로폐기 20%

카운슬의 결론은 building block의 실질이 안정된 CLI 계약이라는 것이었다. 그런데 그 CLI가 1,781줄짜리 단일 파일이고 패키지 경계가 없다. 테스트도 없고, 서버와 버전이 어긋나도 알 방법이 없다.

구현
packages/cli/
  src/commands/*.ts    명령별 분리 (지금은 한 파일에 12개)
  src/context.ts       주소 해석 · 포트 결정
  bin/ttym             얇은 진입점

B3의 @ttym/api를 쓴다. 지금 CLI는 자체 fetchJson· fetchRequest를 갖고 있는데, 이것이 실제로 버그를 냈다 — 반환 구조를 잘못 읽고 소켓 타임아웃이 blocking 요청을 끊었다.

함께 넣을 것
  • 버전 불일치 감지 — CLI와 서버 버전이 다르면 명시적 오류. 오늘 v2 holder와 v3 서버가 섞여 돌았는데 알 방법이 없었다
  • 구조화 출력 계약 — --json의 스키마를 고정하고 exit code를 문서화
  • e2e 테스트 — 생성 · 열거 · 입력 · resize · 종료 · await 한 바퀴
완료 판정

CLI만으로 세션을 만들고 조작하고 지우는 스크립트가 통과한다. 서버 버전이 다르면 조용히 오동작하지 않고 오류로 멈춘다.

문법은 바꾸지 않는다. 주소 체계·동사 정리(new/split 분리 등)는 D2다. 여기서는 구조와 계약만 잡는다.

Phase C — 소유권 분리 URL이 아니라 타입부터. 누가 쓸 수 있는가를 먼저 고정한다.

endpoint 이름은 D 단계에서 바뀔 수 있다. 그래도 C1의 소유권 분리는 남는다.

C3✓프로덕션 fixture 고정폐기 5%

실제 workspaces.json·holder manifest·session meta의 비식별 복사본을 만들어 재기동과 롤백 테스트에 넣는다. reconcile 전후 차이도 출력한다.

오늘 교체에서 드러난 실패 모드들(두 서버 경쟁, 소켓 상실, CLI 응답 파싱)이 전부 실데이터에서만 나타났다. fixture가 있으면 회귀로 잡힌다.

완료 판정

pnpm test가 실제 규모의 데이터로 부팅·복구·롤백을 검증한다.

Phase D — 표면 소속 모델이 확정된 뒤. 이 순서를 어기면 두 번 고친다.

D1✓소속 모델 ADR — 네 질문만 닫는다폐기 10%

저장 포맷은 아직 건드리지 않는다. 다음 넷만 결정한다.

1. 세션과 workspace의 cardinality가 정말 항상 1:N인가?
2. workspace 소속 세션은 반드시 layout leaf여야 하는가?
3. layout은 서버 전역 문서인가, 클라이언트별 view인가?
4. name · role · tags는 session 속성인가, membership 속성인가?

2번이 핵심이다. "소속 세션은 반드시 pane에 보인다"를 불변식으로 승격하면 배치 없는 세션·클라이언트별 뷰·최소화 상태가 전부 닫힌다. headless 조작을 지향하면서 headless 세션을 금지하는 셈이 된다.

하나라도 미확정이면 저장 포맷 변환을 시작하지 않는다. v2 → v3 → v4 두 번보다 v2 → 최종 한 번이 우월하다.

D2✓CLI 문법 정리 — alias로 먼저 얹는다폐기 20%

주소 체계(core:claude · :claude · #42), new/split 분리, remove/terminate 중복 제거.

동시에 깨뜨리지 않는다. 새 문법을 기존 명령의 alias로 먼저 추가하고, 클라이언트를 하나씩 옮긴 뒤, 마지막에 구 문법을 제거한다. "세 클라이언트가 동시에 안 도는 구간"은 받아들일 조건이 아니라 설계 결함이다 — 서버는 이미 HTTP와 WS 양쪽으로 lifecycle을 지원한다.

D1 없이 지금 시작하면 폐기 확률이 65%로 올라간다.

D3✓shadow projection으로 새 저장 모델 검증폐기 25%

v2가 계속 정본인 상태에서 같은 논리 연산을 새 형태로 투영하고, 매 mutation마다 두 투영이 일치하는지 비교한다. 핸들러가 두 파일을 제각각 쓰는 best-effort dual write는 금지한다.

되돌릴 수 없게 되는 지점은 변환기를 실행하는 순간이 아니라, v3로 표현할 수 없는 첫 mutation을 프로덕션에 기록하는 순간이다. shadow projection은 그 지점을 최대한 늦춘다.

하지 않을 것

holder 셀 에뮬레이션 — 대체 holder가 wide char·combining·OSC 8·reflow까지 구현해야 해 교체 가능성이 오히려 줄어든다. 메모리도 한 자릿수 이상 커진다. 재검토 조건: "서버가 무기한 내려가 있어도 고정 저장 한도 안에서 정확한 화면을 복구해야 한다" — 지금 이 요구가 없다.

저장소 플러그인 API — ring·cast·셀 스냅샷은 대체재가 아니라 목적이 다르다. 구현체가 하나뿐인데 계약을 먼저 고정하면 내부 개선마다 호환성이 발목을 잡는다. 두 번째 실제 구현체가 생길 때까지 만들지 않는다.

plugin API · 전면 재설계 — building block의 가치는 독립 배포 소비자가 있을 때 생긴다. 판별식: 이름과 소유자가 있는 소비자가 실재하고, CLI/HTTP 어댑터로 충족되지 않으며, dual-run 무손실 롤백이 증명됐을 때. "향후 native 앱"은 존재로 세지 않는다.
