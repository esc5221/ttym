ttym 설계 재정리 계획

2026-04-21 · 인지부하 진단 및 멘탈모델 재설계 · 대상 문서: ttym-design.html · 작성: tmux/docker/kubectl 학습 패턴 차용
요지. 현재 v2 설계는 정합성이 높지만 학습 곡선이 가파르다. 원인은 두 개의 트리(workspace 안/밖), transport 3개의 평등 노출, 구현 디테일(holder·runtime·annotations)의 표면 노출, 동사가 분류 없이 나열, tmux 사용자에게 매핑 없음 다섯 가지. 재설계의 단일 핵심은 "명사 둘 · 동사 그룹 다섯 · 주소 한 줄"로 좁히고, 나머지는 명사 카드와 구현자 문서로 격리한다는 것.

§1진단 — 인지부하의 원인 5가지

A
두 개의 트리. workspace 안의 session + standalone session 모델이 공존. tmux는 모든 PTY가 단일 트리 (session > window > pane). ttym은 매번 "이 session은 안인가 밖인가" 결정해야 함.
→ INV-1~4가 다 이 모호함을 강제로 닫는 enforcement 규칙.
B
transport 3개가 평등하게 노출. tty · web · native 셋이 명령어 자리에 같이 올라옴. 사용자는 매번 셋 중 하나를 고른다. tmux는 transport가 attach 하나뿐. SSH/mosh는 외부 도구가 알아서.
C
구현이 도메인에 비친다. holder · runtime · annotations · interactions — 사용자에게는 다 구현 디테일. 필요한 건 workspace/session 둘인데 표면에 7개가 보인다. tmux는 server · panes 같은 내부 구조를 사용자에게 안 보여줌.
D
동사가 분류 없이 나열. tty/web/send/await/screen/spawn/kill/pick/ls/whoami 가 일렬로. 사용자는 "내가 하려는 게 어디 있지?"를 매번 스캔. 동사 그룹이 없으면 grid 학습 불가능.
E
tmux 매핑이 문서에 없다. ttym은 tmux로 거의 직역 가능한데 그 줄 하나가 없다. 학습 시간이 분 → 초로 줄 기회를 놓치고 있다.

§2학습 — tmux / docker / kubectl 이 잘 푼 패턴

도구핵심 정신모델ttym에 적용
tmux 단일 트리 (session > window > pane). 각 단계가 시각적 단위. prefix + 한 글자 = 한 행위. server는 안 보임. standalone session 폐기 · 구현은 사용자 표면 밖
docker 동사 5~6개로 90% cover. run = create + start + attach 원샷. ttym new = create + attach 원샷 동사
kubectl verb × noun 그리드. get/describe/create/apply/delete + 모든 noun. -o 일관 출력. 동사를 5 그룹으로 분류 · 한 표로 시각화
git porcelain 사용자용 vs 스크립트용 동사 분리. 일상은 porcelain만. 일상 명령 vs session ... 하위 명령 분리

§3새 멘탈모델 — 세 줄

명사 둘 
workspace  ⊃  session                       (workspace 안의 session들)
동사 그룹 다섯 
COMMUNICATE   tty · web · pick              양방향 연결
SUBMIT        send · await                  단방향 입력 / 응답 대기
OBSERVE       ls · screen · whoami          읽기만
LIFECYCLE     new · kill · session move|rename   탄생·죽음·이동
ADMIN         workspace * · server * · agent *   구조 변경 (자주 안 씀)
주소 한 줄 
workspace[:session]                         (예: core / core:claude / :claude)
#42                                          디버그/도구용 escape hatch
이게 사용자가 외워야 할 전부다. 나머지는 옵션·플래그·invariant — 무한대 → 유한.

§5결단 7가지

1
standalone session 디플레이트. workspace 밖 session = "default" workspace (자동 생성, 보이지 않음)으로 흡수. INV-1~4 거의 사라짐. session.workspaceId optional 제거. 주소가 항상 2단 (ws:name).
2
원샷 동사 new 도입. ttym new claude = current ws에 claude 생성+attach. docker run 위치. spawn은 alias로만 남김. --no-attach로 docker create 대응.
3
동사 그룹 5개를 문서에 시각적으로 명시. COMMUNICATE / SUBMIT / OBSERVE / LIFECYCLE / ADMIN. 모든 도움말이 이 그룹 안에서 검색됨. 한 표로 정리.
4
tty가 기본, web은 명시. 가장 잦은 attach 행위 한 단어. ttym attach는 tty의 영구 alias (tmux 근육 기억).
5
구현 단어를 사용자 문서에서 제거. holder · runtime · annotations · interactions 같은 단어는 §아키텍처(구현자용)로 분리. 사용자가 일상에서 만지는 건 workspace · session 둘뿐.
6
invariant는 명사 카드 안에 인라인. INV-1~7 별도 섹션 폐기. workspace 카드 안에 "workspace 규칙", session 카드 안에 "session 규칙" — 명사를 볼 때 같이 보인다.
7
학습 경로 §추가. Day1 / Day2 / Week2 / Month1. 첫날 5개 명령으로 90% 가능. 점진적으로 placement · agent hook · 옵션.

가장 큰 단일 결단 — 다시 강조

standalone session 개념을 사용자 표면에서 지운다. 이 한 결단이 인지부하의 50%를 제거한다. 모든 session이 workspace 안에 있으면 INV-1~4 거의 사라지고, 주소가 항상 2단, session 카드의 상태기계가 단순해짐. backend에 default workspace를 자동 생성해서 standalone PTY를 거기 넣으면 기능은 그대로.
이 계획은 ttym-design.html 의 정합성을 유지한 채 구조와 학습 곡선만 재설계한다. INV-1~7 · API endpoint · WS wire spec 등 기술 결정은 그대로 살아남고, 위치와 표현만 바뀐다. 승인되면 다음 단계는 §0~§2 부터 새 문서로 작성.
